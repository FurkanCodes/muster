# Muster — architecture

Draft for milestones 1–2. What Muster does and why lives in [PRODUCT.md](PRODUCT.md) (`PRD-*`). This file says how it is built (`ARC-*`). The study of Nebula that informed it is in [docs/research/nebula-study.md](docs/research/nebula-study.md); Nebula is MIT-licensed, and if any of its code is ever copied, its notice goes into `NOTICE`.

## 1. Shape

```
┌──────────────────────────────── host ────────────────────────────────────┐
│  muster (TUI) ─┐                                                          │
│  muster run …  ├── Unix socket, 0700 ──┐                                  │
│                                        ▼                                  │
│  ┌──────────────────────────── muster daemon ──────────────────────────┐  │
│  │ Supervisor: owns every session and run, calls the pure machines     │  │
│  │ Store (SQLite, own thread) · Scheduler · Sampler · Sources · GitHost│  │
│  │ Hook receiver (Unix socket, per-session tokens)                     │  │
│  └───────┬──────────────────────────────────────────┬──────────────────┘  │
│          │ PTY                                      │ Docker API          │
│          ▼                                          │                     │
│  hands-on sessions in git worktrees                 │                     │
│  (claude, codex … as the user)                      │                     │
└─────────────────────────────────────────────────────┼─────────────────────┘
                                                      ▼
                        containers: hands-on sessions (exec with a TTY)
                        and runs (headless agents, checks by exec)
```

The daemon is the only process that owns agent processes and talks to Docker, GitHub and ticket sources. Clients talk only to the daemon. A container sees only itself.

## 2. Core model

- **Workspace** — where code lives: a `Worktree` (a git worktree on the host), a `Checkout` (the project's own folder: its repository's main checkout, or a plain folder) or a `Container` (a container with its own checkout).
- **Session** — one agent process in one workspace. Its **driver** is `Pty` (hands-on: a person can type) or `Headless` (structured JSON output, driven by a run). A session can switch driver: take-over stops the headless process and resumes the same agent session interactively; hand-back does the reverse.
- **Run** — one ticket going through the stages in `PRODUCT.md` §5. A run owns a container workspace and creates sessions in it: a builder, then a reviewer.
- **Action** — *Check*, *Draft PR*, *Agent review*. The run machine chains them; on a hands-on session the user triggers them one at a time, and they execute in that session's workspace.

## 3. Workspace

| Crate | Holds | Rule |
|---|---|---|
| `muster-core` | IDs (ULID newtypes), entities, protocol types, typed error codes, harness descriptor types | No IO (`ARC-01`) |
| `muster-state` | The pure state machines: session status and run stages, each `step(state, event, now) -> (state, Vec<Effect>)` | No IO, no async, injected clock (`ARC-01`) |
| `muster-daemon` | Supervisor, store, IPC server, PTY host, container runtime, hook receiver, scheduler, sampler, sources, git host, harness drivers and parsers | Every external system behind a trait (`ARC-03`) |
| `muster-client` | The async framed transport over the socket, and a client connection that performs the handshake; shared by the daemon, the TUI, the binary and the e2e tests | No business logic |
| `muster-tui` | ratatui client: sessions, needs-you, terminal view, dialogs | Renders state; holds no business logic |
| `muster-notch` | The notch on a Mac (§5b): a client that shows the agents around the MacBook's notch through AppKit | A client like any other (`ARC-22`); its only `unsafe` is AppKit's (`ARC-12`) |
| `muster` | The binary (clap): no args opens the TUI; `daemon`, `status`, `project`, `worktree`, `session`, `issue`, `run`, `auth`, `notch` | Thin |

Main dependencies: tokio, portable-pty, vt100 + tui-term, the `docker` command (Docker), rusqlite (bundled), serde + rmp-serde, toml + toml_edit (settings, read strictly and changed keeping the person's comments), ratatui + crossterm, axum (hook receiver), clap, the `gh` and `glab` commands (GitHub, GitLab), reqwest with rustls (Bitbucket's, Jira's and Linear's APIs, MCP servers, OAuth), sha2 + base64 (PKCE), the `security` command (macOS Keychain), sysinfo, tracing, ulid; on macOS, objc2 with its AppKit, Foundation, Quartz Core and dispatch bindings, each without its default features (the notch).

## 4. Daemon

- **One owner.** A single Supervisor task owns every session's and run's state and is the only thing that calls the machines. The PTY host, container runtime, hook receiver, sampler, sources and git host are tasks that report events to it over channels and carry out the effects it hands out. No shared mutable maps (`ARC-02`); Nebula's thirteen mutex maps with lock order kept in comments are the thing to avoid.
- **Store on its own thread.** One rusqlite connection (WAL) on a dedicated thread, fed commands over a channel. Async code never blocks on SQLite, and keystrokes never touch it.
- **Write-ahead transitions.** A transition and its reason are committed before its effects run (`ARC-10`). Effects are idempotent: "open draft PR" first looks for an existing PR on the branch; "start container" first looks for a container with the run's label.
- **Lifecycle.** The TUI auto-starts the daemon when the socket does not answer, with `muster daemon --detach`, which starts the daemon itself as a process of its own (`--background`: `setsid`, no controlling terminal) and exits at once, the UI reaping it. The daemon is so never the UI's child: whatever ends the UI, a terminal pane that kills its whole process tree included, leaves the daemon and its sessions running (`PRD-09`); seen 2026-10-12, when a daemon that was the UI's child went down with it, silently, several times a day. In the background a hang-up (SIGHUP) is logged and ignored, by a handler rather than by ignoring the signal outright, which agents would inherit and which Muster stops them with; run in a terminal, a hang-up stops it, as its terminal has closed. Every stop logs its signal. Tested by killing the UI's whole process tree, and by a hang-up.
- **Restart in place** (`muster reload`, `muster upgrade`, `handoff`): SIGUSR1 has the daemon move onto the program installed now as the same process, like Nebula's `nebula reload`, so every session's program stays its child and runs on untouched; clients reconnect, as they do after any restart. First the new program must say it can take over the handoff's format (`muster daemon --can-adopt <format>`), so an older Muster is never handed sessions it cannot hold. Then each terminal's actor stops its reader between reads (it waits with `select`, as macOS's `poll` does not work on terminals), so no byte leaves the terminal that the ring does not hold, and hands over the terminal, its ring, input modes (kitty flags, bracketed paste, mouse) and size; the Supervisor adds each session's machine (carried with its moments as how long ago, `muster_state::session::Carried`), hook token, harness and how long it has run. That goes, MessagePack, into a file opened 0600 in the private runtime directory and unlinked at once, and the lock, both listening sockets, the terminals and that file are kept open across `exec` of the program with its own arguments and `--adopt <descriptor>`. The new image takes each over (`handoff::inherit`, checking each is the kind of file it should be, and closing it on `exec` again so no program it starts inherits it), adopts the sessions before recovering any (`Supervisor::adopt_sessions`), and serves on the same sockets, connections made meanwhile having waited in the backlog. If `exec` fails, the daemon takes its sessions back the same way and carries on. `muster reload` refuses a daemon from before 0.2.0, which SIGUSR1 would end, and reports what the daemon logged: taken over, with how many sessions, or why not. `muster upgrade` downloads the release's archive for the machine, checks its SHA-256 before anything is replaced, unpacks it beside the program and renames it over it (running programs keep theirs), then reloads. Sessions whose program had already ended are not carried: their output is no longer kept, as after any restart. Tested end to end: a shell keeps a variable and finishes a command started before the reload, a Claude Code session's hooks still move its status with their old token, the daemon keeps its pid; and an upgrade against a stand-in release, replaced on a matching checksum and left alone on a wrong one. `muster daemon` runs it attached for development. `muster daemon stop` stops whichever daemon answers, also one from another build: its hello offers every protocol version from the first, and every version's welcome (and, from protocol 2, its refusal) carries the daemon's pid. Runtime and data directories come from `MUSTER_RUNTIME_DIR` and `MUSTER_DATA_DIR` when set, so every test gets its own.
- **Restart** (`PRD-09`):
  - *Containers* outlive the daemon (`ARC-04`). On boot the daemon lists containers labelled `muster.workspace=<id>`, matches them with SQLite, and re-attaches each stream from the last stored offset. A missing container moves its run to *Needs you* with that reason.
  - *Worktree sessions* die with the daemon, because it holds their PTYs. On boot each one is relaunched with the harness's resume (`claude --resume <session-id>`) in the same worktree. A resume that exits within 10 s falls back to a fresh session with a note, as Nebula does. A resumed session starts finished, and unseen if the restart cut a turn short; its hooks get a new token. Sessions whose harness cannot resume (`shell`), whose resume id was never saved (no turn ran), or whose transcript is gone are recorded as exited with an error and marked unseen.

## 5. Sessions

### Hands-on in a worktree (M1)

- **PTY host:** portable-pty spawns the harness in the worktree as the user, with the user's environment minus the markers a parent Claude Code session or its host app sets (an explicit list: identity, sockets, account, effort; one inheriting `CLAUDE_CODE_CHILD_SESSION` would not save its transcript), keeping the person's own settings such as `CLAUDE_CODE_USE_BEDROCK` or `CLAUDE_CODE_OAUTH_TOKEN`. One reader thread per PTY feeds a bounded channel (backpressure); a pump batches output (up to 8 KiB or 5 ms, sent at once after a quiet spell so typed echo is never delayed) into a 1 MiB ring numbered by byte offset and broadcasts it.
- **Attach:** `Attach { session, from_seq }` replays the ring and continues live; a client that falls off the ring gets the whole ring and resets its parser. A session keeps its id when its program is started again (a failed resume's fresh start), and each client follows it through a channel holding the session's current terminal: its stream moves to the new program and its keystrokes go there. The new program's output is numbered on from the old one's, past a gap of one, so every client starts it on a clean screen and no position from before is mistaken for one after; it keeps the old terminal's size.
- **Watching:** while a client is attached to a session and its person is looking, the session is *watched*: nothing that happens in it is news, since the person sees it happen, so a turn that ends or a program that exits in front of them leaves no unseen mark. A client whose window loses focus says so (`Watch { watching: false }`) and says when it is back, and attaches without watching while out of focus (`Attach { watching: false }`), so selecting a session meanwhile clears nothing; terminals that never report focus count as looking. A session whose terminal is no longer held (it ended with an earlier daemon) has nothing to watch, but attaching to it to look still clears its news. The connection holds one guard per watched session; however the watch ends (looking away, detach, disconnect), dropping the guard ends it.
- **Stop:** SIGHUP to the child's process group, then SIGKILL to it after 3 s. A natural exit is told apart from a deliberate stop. Processes that moved to another process group are not reached yet.
- **Exit:** announced only once all output is in the ring, waiting at most 2 s after the process exits, since a background job can hold the terminal open. The terminal's output stays readable after the exit until its worktree is removed.
- **No inherited descriptors:** an agent must not inherit the daemon's sockets or files. macOS cannot create a socket close-on-exec in one step, so a spawn racing a `bind` can leak a listening socket into the child, which then keeps a dead socket accepting connections (seen in the e2e tests). portable-pty closes every descriptor above stderr in the child before `exec`; a test asks `lsof` what an idle shell holds.
- **Worktrees:** created with `git worktree add` under `~/.muster/worktrees/<repository>/<branch>` (`MUSTER_WORKTREES_DIR` overrides it), on the branch the user names — checked out if it exists, created from the current commit if not — or on `muster/<six random characters>` (`worktree-<six>` where the project's branches go without `muster/`, as six alone can read as a commit). They stay out of the data directory because on macOS its path contains a space, which some build scripts mishandle. Removing a worktree deletes its directory and keeps its branch; uncommitted changes need `force`, and running sessions block it. The worktree's metadata in the repo's `.git` is git's own mechanism; Muster writes nothing else into the user's repository (`ARC-05`).
- **The project's own checkout:** adding a project makes its repository a workspace too (`Checkout`), so sessions can run where the person works, as in Nebula; projects added earlier get theirs when the daemon starts. Muster never removes a checkout. Removing a project forgets it and everything stored about it, never touching the repository; it is refused while the project has worktrees (forgetting them would leave their directories unknown) or running sessions.
- **Plain folders:** a project can be any folder, not only a git repository (`PRD-04`). Its checkout's branch is empty; sessions and checks run in the folder; what needs git (worktrees, tickets, reviews, pull requests, runs) is refused with a reason (`BadRequest`) rather than left to fail in git or `gh`. Whether a project is a repository is read from its folder when asked (a `.git` directory, or a `.git` file as a worktree has), never stored, so `git init` there makes it one without telling Muster: the branch watcher shows its branch, and the rest follows. A folder inside another repository is a plain folder: that repository's branches and worktrees are not its own.
- **Worktrees made or removed outside Muster** (by hand, or by an agent running `git worktree add`): every 3 s a task stats each repository project's `.git/worktrees` directory (plain folders are skipped: git, asked there, would answer for a repository around them), which git touches whenever a worktree comes or goes, and Muster's worktree directories; only on a change (and once a minute regardless) it asks `git worktree list --porcelain -z`. The Supervisor adopts a listed worktree no workspace has, if its directory is there, and forgets one git no longer has, if its directory is gone and nothing runs in it, then lets git prune its record so the branch is free. The directory checks keep a list taken a moment before Muster's own add or remove from undoing it.
- **Branches:** what each workspace has checked out changes under Muster (`git switch` by the person or an agent). Every 2 s a task reads each workspace's HEAD straight from git's files (a `.git` directory, or a worktree's `.git` file naming its git directory) on a blocking thread, rather than running git per workspace, and the Supervisor stores and announces those that changed. A detached HEAD reads `detached at <commit>`; a folder with no `.git` reads as no branch; a workspace that cannot be read keeps what it had.
- **What changed** (`changes.rs`, `supervisor::changes`; `PRODUCT.md` §6): git in a worktree or checkout says what is not committed (`git diff -M <HEAD>` with `--name-status -z` and `--numstat -z`, and `ls-files --others --exclude-standard`, an untracked file's lines counted by reading it, up to 200 files of up to 1 MiB, a link never followed) and what the branch's commits changed since it left its base (`base_of`: the settings' `base_branch` or the remote's default; `merge-base`, `rev-list --count`, `log` of the newest 50, and the same diffs from the merge base to `HEAD`), read by `muster_core::changes`, pure. A repository with no commit yet is measured against the empty tree, and a branch with no base found shows only what is not committed. Revisions follow `--end-of-options`, and diffs are asked `--no-color --no-ext-diff`, so the person's git settings cannot change what is read. Git's output is read as printed, not trimmed (a NUL-separated listing can start with a space), and only up to a limit (`git::capped`), git stopped past it: a file's diff is cut at 512 KiB, at a line's end, and says so. A diff is asked only of a file git lists as changed in that part, so a path a client names can reach nothing else (`git diff --no-index` with `/dev/null` for an untracked one). The text is cleaned of control characters but tabs and line breaks before it is sent, and code is never stored or logged (`PRD-06`). Each workspace keeps a summary (`Workspace::changes`: files, lines added and removed, both parts together), never stored, sent as `WorkspaceUpserted` (protocol 24, an optional field older clients pass over) and looked at again, off the loop with the git deadline, when a session there stops working (`Running` or *needs you* to anything else, whatever the harness), when its branch changes, on the pull request timer (every tenth tick while no client is subscribed), and whenever a client asks for the whole (`WorkspaceChanges`; `FileDiff`, sent only to a daemon of 24 or later), so the line agrees with what the person reads. A run's container and a plain folder are refused with a reason.
- **Timeline** (`timeline.rs`, `timeline/undo.rs`, `supervisor::timeline`; `PRODUCT.md` §6, `PRD-14`): each workspace on the host in a repository has a bare git repository of Muster's own, `<data>/timelines/<workspace>` (its folder readable by the person alone), that borrows the repository's objects (`objects/info/alternates`), so a snapshot writes only what is new. A snapshot is `git add -A` and `write-tree` in the workspace with the store's own index and object directory (`GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`), `.gitignore` honoured, untracked files over 32 MiB left out, and settings that would write in the repository (`core.splitIndex`, `core.fsmonitor`) turned off; the person's index, refs and objects are only read. Git, finding there an object a snapshot needs, refreshes that object's file time, as it does for any repository borrowing another's objects, which also keeps it from being pruned there. An entry is a commit under `refs/timeline/<number>` holding the files as it left them, whose one parent has none and holds the files as it found them, so letting an entry go frees what only it held; its message is a few `key: value` lines (`muster_core::timeline`, pure): its kind (an agent's *turn*, the edits *between* turns, an *undo*), its session and agent, when it began and ended, what it changed, and the commit checked out before and after. A turn under way has its start under `refs/open/<session>`. Turns come from statuses, whatever the harness: a session of an agent (not a shell) going from anything else to `Running` or *needs you*, or starting with its first prompt, begins one; going back ends it. At a turn's start, what changed since the newest entry is an entry of its own, unless another agent works there. A turn that changed no file and moved no branch is no entry. Snapshots run off the loop, one job at a time per workspace, so a turn's end never overtakes its start (at most 32 waiting, `ARC-14`; one gone half an hour is taken as lost). The newest entry's number is on the workspace (`Workspace::timeline`, never stored), so a client asks again when it changes; `Timeline`, `EntryDiff` and `UndoPlan` read the store; `Undo` (protocol 25, sent only to a daemon of 25 or later) is refused while any session there works, then, as a job: checks git still has everything the entry began from, keeps what is there now, refuses if a file it would write over is there yet kept by no snapshot (ignored, or too large; git itself writes over ignored files), puts the files back with `read-tree -m -u` from the snapshot just taken to the entry's start, so a refusal changes nothing, and with the person's say-so moves the branch with `reset --mixed`: back only over commits no remote-tracking branch has, forward again, or back from where it has moved another way (a rebase, a tidy) where nothing it would leave is on a remote. The undo is an entry, which can be undone in turn. The store keeps the newest 100 entries (`git gc --prune=now` once 20 more have gathered, `gc.auto` off) and goes with its workspace (`ARC-14`). Store commits are made with Muster's own name and date and `--no-gpg-sign`, and nothing of the person's code is logged (`PRD-06`).
- **Where work meets** (`clashes.rs`, `supervisor::clashes`, `muster_core::clashes`; `PRODUCT.md` §6, `PRD-14`): each project on the host in a repository has a store of the timeline's kind, `<data>/clashes/<project>`, with an index for each workspace (`indexes/<workspace>`), so the workspaces' snapshots never wait on each other's or a timeline's. Of the project's workspaces whose work changes something (a summary, above) and whose pull request has not merged, the newest twelve are compared: each one's snapshot is kept under `refs/snapshots/<workspace>` (so tidying keeps what its index names), what its work changes since it left its base (`merge-base` with `base_of`, or its last commit where none is found) is listed from the snapshot (`diff --no-renames --name-only`), and each two that change a file alike, or one a file where the other has a folder, are merged in the store by `git merge-tree --write-tree --name-only` (git 2.38 or later; where git cannot merge them, the files are shown as shared alone) on commits of their snapshots on their last commits, so git finds their merge base itself. Of the files git cannot merge, only those both change count: a conflict in a file only one changes is with what its base has since, not with the other's work. Each workspace keeps what was found (`Workspace::clashes`, never stored, protocol 26, a field older clients pass over): each other workspace with how many files both change, how many would conflict, and the first 20, those that would conflict first. A look runs off the loop with git's deadline, one at a time for each project (one asked meanwhile follows it; one gone ten ticks is taken as lost), when a look at changes finds a workspace's summary moved or follows a turn or a client's asking, when a branch changes under a workspace or its pull request merges or stops being merged, and every tenth pull request tick. A workspace's clashes go when its branch changes, and others' with it when it goes; snapshots of workspaces gone go with the next look, loose objects past 2,000 with `git gc --prune=now`, and the store with its project (`ARC-14`). Paths are sent; no code is stored or logged (`PRD-06`).
- **Stacked work** (`supervisor::stacks`, `timeline/moving.rs`, `muster_core::stacks`; `PRODUCT.md` §6, `PRD-14`): `CreateWorktree` and `StartFromIssue` take `on`, a workspace of the same project whose branch a new branch is made on top of (`git worktree add -b <branch> <path> <its newest commit>`; refused for a branch that exists, or one not checked out). The workspace keeps the branch it is stacked on and the commit of it its work follows (`Workspace::stacked_on`, stored: schema 6, `stacked_on` and `stacked_at`). While the repository has that branch, it is the workspace's base for what changed, where its work meets others', a review, a tidy and the pull request (`stacks::stacked_base`). `MoveOnto` (protocol 28, sent only to a daemon of 28 or later) is refused while an agent works there and runs as a job on the workspace's timeline: refused where anything tracked is not committed; the target is the stacked-on branch's newest commit, or the base's once that branch has merged (its worktree's pull request says merged, the branch is gone, or the base has its commit), or the base's where it is not stacked; the commits it replays are those after the commit it follows (or its merge base with the base), refused where it no longer follows it or it is on the newest already. What is there is kept first, then `git rebase --onto <target> <that commit>` (with `rebase.updateRefs` and `rebase.autoStash` off and no editor); one that stops is aborted, saying which files would conflict, so nothing changes. The move is an entry of its own (`EntryKind::Moved`, told to a client older than 28 as edits between turns, `Reply::for_version`), so `z` puts files and branch back; what the workspace is stacked on is then as the move left it. Muster pushes nothing: a pull request follows a moved branch once the person pushes it.
- **Tidying commits** (`tidy.rs`, `supervisor::tidy`, `muster_core::tidy`; `PRODUCT.md` §6, `PRD-14`): `TidyCommits` (protocol 27, sent only to a daemon of 27 or later) starts the coding agent the person picked (not the review, a shell or the checks) in a worktree or checkout on the host, on a branch, as a session titled *Tidy commits · <agent>*, with a prompt naming the commits to tidy (`runs::prompts::tidy_by_hand`). It is refused while any session there works, while anything git tracks is not committed, and when there is nothing to tidy: the commits taken are those on no remote and not in the base (`rev-list HEAD --not --remotes <base>`), which must be the newest, in a line with no merge; none of them pushed, so no force push is ever needed. The agent's first turn is in the workspace's timeline, which keeps the files as they were, so `z` puts them back and the branch with them (back from where it moved another way, as nothing it leaves is pushed). What the tidy began from (the commit the tidied ones follow, the committed tree and `HEAD`) is kept by the Supervisor for the session, and each time its agent stops Muster checks, off the loop: untouched; the branch no longer following that commit; the files, committed or not, differing from the tree (`git diff <tree>`); changes left uncommitted; or the files as they were in so many commits. What it found is on the session (`Session::tidy`, never stored, a field older clients pass over), and what it began from goes when the session ends or goes (`ARC-14`).
- **Git:** run without a shell, with a 2-minute limit and without inherited `GIT_DIR`-style variables. It runs while the Supervisor waits, so a slow checkout delays other commands and status updates, though never keystrokes; moving it off the Supervisor is a later step if it hurts.

- **Restart and removal:** an ended session can be started again in place (`RestartSession`): the same session id and row, the stream continuing as for any relaunch; Claude Code resumes its saved conversation when its transcript is still there, and starts fresh otherwise. An ended session can be taken off the list (`RemoveSession`); like a removed worktree's, its row and history stay in the store. The UI closes a running session in one step, after asking once: it asks the daemon to stop it, remembers it, and takes it off the list as soon as the state shows it ended; if the stop is refused, it is not closed.

### Hands-on in a container (M2)

- **Where:** a run's container is a workspace of its project (`Container { run, branch }`), made the first time a session needs it and removed when the run ends and its container goes. In it the person drives the run's agent by taking the run over (§7), or opens shells to look around; Claude Code starts there only through a take-over, since the run's own agent works there otherwise.
- **How:** `docker exec --interactive --tty` under the daemon's own terminal, feeding the same ring and attach protocol; resizing the daemon's terminal resizes docker's, which resizes the program's. Values for the program (the terminal type, the session, and for Claude Code the runs' credential, `PRD-06`) go through docker's environment, never its arguments. Hooks cannot reach the daemon's socket from a container, so status comes from the terminal's progress sequence and the process.
- **Stopping:** stopping docker's client stops nothing in the container, so a script started with the program records its process under `/tmp/muster/sessions/`, and stopping sends that process group a hangup (an interactive shell ignores a plain terminate) and a kill two seconds later if it is still there. A pid is trusted only if that process carries the session in its environment, since pids are reused; a session started again (by the person, or after a daemon restart) first stops the program it ran before. Tested against the real Docker.
- **Restart:** the run's agent, while the person has the run, starts again after a daemon restart, resuming its conversation; shells are recorded as ended and stopped in the container.

### Status

- **Signals:** harness hooks, the terminal progress sequence (OSC 9;4), the window title (OSC 0/2) of a harness that says its state there, and process exit for hands-on sessions; the JSON output stream for headless ones (a finished turn is a `result` event).
- **Hooks without editing config** (`PRD-13`, `ARC-05`): Claude Code takes extra settings at launch through `--settings <json>`, so its hooks are passed on the command line and never written to disk; the other agents are heard as §7 sets out. Each hook runs `curl --unix-socket <runtime>/hooks.sock` with the session's own token from its environment, posting to `/hooks/<harness>` (or `/hooks/<harness>/<event>` for a harness that names its events only in the address), times out after 3 s, and never fails the agent. The receiver (axum on that socket) answers at once and only queues the body; the Supervisor takes a token only at its own harness's address and has that harness read the body, field by field, so a changed field loses only itself. Verified against Claude Code 2.1.291: inline `--settings` hooks run, `--session-id` is honoured, and the fields read are present. A harness without a launch-time option runs without hooks, and its status comes from the progress sequence and process state.
- **Terminal questions:** programs ask their terminal things at startup and wait for answers; Claude Code 2.1.291 asks for keyboard-protocol support, device attributes and the terminal version. The terminal actor answers them, plus device status and cursor position (from a screen built only when first asked), and which private modes the terminal has (DECRQM, `CSI ? Ps $ p`), which Claude Code 2.1.296 asks once the version is answered, for synchronized output (2026) among them: a mode the actor tracks is answered set or reset, any other as not recognized, so nothing waits out a timeout. It tracks kitty keyboard flags and bracketed paste for clients. Adapted from Nebula, which leaves the version query unanswered.
- **Synchronized output:** a program that knows the terminal has it draws each frame between `CSI ? 2026 h` and `CSI ? 2026 l`. A client follows these in the output of the session it shows and holds its drawing while a frame is half drawn, at most 150 ms in case one is never finished, so frames are seen whole, as in terminals that have the mode.
- **Identity** (`ARC-11`): every session gets its own random token, and the receiver derives the session from the token. Nebula shares one token per boot and trusts the session id in the query string; Muster does not.
- **What an agent is doing:** the same hooks name the tool each agent uses (Claude Code, Gemini CLI, OpenCode, Copilot CLI), and Claude Code's and Gemini CLI's carry its input, so the daemon keeps a short phrase for each working or waiting session (`harness::activity`, pure): `editing view.rs`, `running cargo`, `reading docs.rs`, `wants to run rm`, `thinking`. Only what a glance needs: a file's name, never its path; a command's program, never its arguments, which can carry a secret (`PRD-06`); a web page's host; cleaned of control characters and cut to 40 characters. It is cleared when the turn ends or the session stops working and waiting, sent to clients as it changes (`SessionActivity`) and in the snapshot, and never stored or logged. Each status carries when it began (`status_since`), from the store's history of changes after a restart, so a person sees how long an agent has run, waited or sat finished.
- **Machine:** pure, with an injected clock and exhaustive unit tests (Nebula's best pattern). States: `Fresh` (launched, nothing asked yet), `Running`, `NeedsYou` (a permission prompt or question, several of which can be open at once; an action required, when a harness's own display says it waits without saying for what; or, for a harness that announces its start, silence for 10 s after launch, since Claude Code 2.1.296 runs no hook while its trust question, a sign-in or first-run setup is on screen and otherwise announces itself in under a second; any hook ends that wait, restoring the status and unseen mark from before it), `Finished`, `Exited`, plus an `unseen` flag. The machine reports its next deadline, so the daemon wakes it exactly when a grace period ends instead of polling. It keeps Nebula's hard-won rules: ignore hooks from a different agent session in the same directory; hold `Running` while subagents still work; clear a permission wait only on a tool event from the one who raised it. It drops the screen-scraping and timing tricks.

## 5a. Terminal UI

- **Shape:** `model` mirrors the daemon's state from the snapshot and deltas; `app` is a state machine with no IO that turns keys, pastes and frames into frames to send; `view` draws it with ratatui; `runtime` owns the person's terminal and the link to the daemon. So every behaviour is a unit test, drawn into ratatui's test buffer.
- **Link:** `muster` with no arguments connects, and if nothing answers it starts `muster daemon --detach` (which starts the daemon apart from the UI and its terminal, §4, so closing either leaves it running) and logs to `daemon.log` in the runtime directory, which the daemon sets aside as `daemon.log.1` (up to `.6`) each day or past 10 MB (`ARC-15`, `log_files.rs`). A lost connection is shown and retried every half second; on reconnect the UI re-subscribes and re-attaches from the last byte it has. The client connection splits into a sender and a receiver for this.
- **Sessions:** the selected session streams into the pane beside the list. ⏎ (or a click on it) gives it the keys there, with the list still in view, and `f` gives it the keys full screen; either way every key goes to the program but Shift-Q, which gives them back to the list, as does a click on the list. Shift-Q, the person's choice over Ctrl-Q (2026-10-12), is easy to find, at the cost of a capital Q: most terminals send it as `Q` itself, so it can never be typed in a session (with the kitty protocol it comes as `q` with Shift, which is taken too). Ctrl-Q reaches the program. Ctrl-] still works (sent as byte 0x1d by terminals without the kitty protocol, which crossterm reports as Ctrl-5, so both are accepted), but needs Option on many layouts. On the list, Shift-Q does nothing, so pressing it once too often never quits. A program draws for its terminal's size, so a session's terminal is always sized to where it is shown: the pane beside the list (whose bottom bar keeps to one line while the session has the keys, so its size holds), or the window below the top bar full screen; going full screen and back resizes it. Keys are encoded from the program's modes — kitty flags, bracketed paste, application cursor keys — which the daemon sends with every attach and on change (`Modes`), since a client parsing output alone loses them once the ring has wrapped. The person's terminal gets the kitty protocol when it supports it, so Shift+Enter reaches Claude Code.
- **Mouse and scrollback:** the UI asks the person's terminal for presses, drags and the wheel (not every movement). In a session's terminal, a program that asked for the mouse (modes 9/1000/1002/1003, encodings 1005/1006, tracked by the daemon with the other modes, as xterm and iTerm2 do: the one set last is in effect and resetting any stops the reports, while an encoding is reset only by its own number) gets the events inside its pane (or below the top bar, full screen), at positions in its own screen, encoded as it asked; otherwise the wheel scrolls the client's own scrollback, or on the alternate screen, which keeps none, sends arrow keys as terminals do. The wheel is the session's wherever the pointer is while it has the keys, and a click on the list beside it, or on the top bar over it full screen, gives the list the keys back. Typing returns to the newest output. A drag with the left button, once it has gone two cells or onto another line (a click the hand moved is still a click), selects the session's text, in reading order over its screen as shown, and letting go copies it (`Action::Copy`), each line's trailing blanks left out: the person's terminal can only select whole lines of the window, the list and borders with them. A program that asked for the mouse gets drags but for one with Shift. The cells stay reversed until the next click, key, paste or turn of the wheel. The runtime puts the text on the clipboard with the system's own program (`pbcopy`; `wl-copy` or `xclip` on Linux) where the UI runs on the person's machine, else, over SSH or with none, by asking their terminal (OSC 52). In the list, the wheel moves the selection or scrolls the preview (a program that takes the mouse, as Claude Code does on its full-screen views, is sent the wheel to scroll its own), and clicks select, or open the session shown: a project's or a worktree's details open nothing, so no dialog, which takes no clicks, opens by surprise; the lists keep their scroll offset in the app, so the view moves only when the selection would leave it, and clicks map to what is drawn.
- **Motion:** a running session's mark spins (a braille spinner, a frame each 100 ms) and what needs the person pulses, its ▲ and the *Needs you* count going bright, plain, dim and plain again. A session whose status changes to finished, ended or waiting on the person flashes its line in the sessions list and *Needs you*: lit in the status's colour for half a second, tinted with it for another, then settled; a new session or a snapshot flashes nothing, so reconnecting lights up nothing. A selected line gives way to its flash. The times on sessions' lines tick each second while a session runs or waits (each minute otherwise), and a note under the screen dims after four seconds and goes after five, giving the keys' hints back; an error stays until the next key. Kep, at the top bar's start, blinks for two steps in forty while something works, and is glad (`▼^ᴥ^▼`) for three seconds after a session finishes. On the selected line of *Sessions* or *Needs you*, a session's title or a worktree's branch that the line cuts short rests a second and a half, then slides along five characters a second, an ellipsis at either end for what is out of view, until its end shows; it rests there and starts again, so the whole name can be read. Only the selected line's slides, only while the list has the keys and the window is looked at, and from its start each time the line is selected again. Nothing else moves. The runtime counts the steps from its start and hands the step to the app; the view draws the step it is given and never reads the clock (`ARC-03`), so drawing stays a function of the app and is tested at any step. Only while a session runs, something waits on the person, a line flashes, Kep is glad, a note fades or a name slides does a new step ask for a frame (a sliding name, only as it moves) (and once more as a flash ends, to settle its line); otherwise nothing is drawn for motion. The runtime also reads the wall clock for the times and hands it to the app (`on_clock`), which asks for a frame only when a time shown would read differently. `MUSTER_MOTION=off` keeps every mark still, Kep's face too, every name cut short where it is cut, and the times to the minute.
- **Look:** the top bar starts with Kep's face (below) and, after the tabs, counts the agents working, waiting on the person and done, in their statuses' marks and colours, then the machine's memory as a bar of eight cells (green, yellow past 70%, red past 90%) and the daemon's version, as much as fits. Each project has a colour of the terminal's own sixteen (blue, magenta, cyan and their light forms, apart from the statuses' yellow, red and green), by its place in the list: its name is in it, and its rows on every list start with an edge in it, which on the selected line is a full block, the selection's bar; the selected line is tinted (a dark grey background, its text at full strength) rather than reversed. A session's line reads its mark, its title, what it is doing (its activity while it works or waits, else its status) and, at the end, how long it has been so (`4m12s`, `12m ago`); short of room, the title gives way first, then a finished session's time, then what it is doing, which is cut short only while it works or waits. Its pane's title says the same, with its use of memory and CPU and what its agent has used (`1.2M tokens`, or `$0.42 · 40k tokens` where the agent reports a cost, §7), as does its bar full screen. A worktree's line ends with the pull request from its branch, as its git host last said (§10): its number, then while it is open its review's word (`approved` green, `changes` red, `review` yellow) or else `open` or `draft`, and a mark for its checks (✓ passed, ✗ failed, ◌ running); once over, `merged` (magenta) or `closed` (dim). Short of room the word goes first, then the branch is cut short. Its details say the same in words (`#42 · open · checks passed · approved`), and `b`, on it or one of its sessions, opens it in the browser (http and https only). On a ticket's line each agent is its letter (C Claude, X Codex, G Gemini, O OpenCode, P Copilot) and its mark. Screens with nothing on them yet say so: *Needs you* empty is *All clear*, and before the first project, or while connecting, the pane shows Kep beside Muster's name drawn large. **Kep**, Muster's sheepdog (Muster gathers sessions as a sheepdog musters a flock), is drawn in half blocks in the terminal's own colours (a black-and-white coat, Muster's cyan for its bandana), 24 cells by 9, and where that does not fit the name stands alone. As the UI starts, a welcome fills the window: Kep, the name, and how the sessions stand (*Welcome back. 2 working, 1 waiting on you.*); it stays a second and until the state has come or the daemon is found out of reach. A key lets it go and does what it says, as a person who knows the screens types ahead; a click or the wheel only lets it go, as it points at nothing the person can see. At the top bar's start Kep's face, six cells, says how the flock stands: `▼•ᴥ•▼` watching while something works, `▲•ᴥ•▲!` ears up and barking (the `!` pulsing) while a session asks or wants a look, `▼^ᴥ^▼` glad of a finish, `▼-ᴥ-▼ᶻ` asleep while nothing works or waits, `▼;ᴥ;▼` while the daemon is out of reach. A question asked comes before a finish's gladness, which comes before an unseen session's look. Kep is the first to go short of room: it is drawn only while all the rest of the top bar fits beside it in full.
- **Notifications:** while its window is out of focus, the UI tells the person when a session newly needs them (a wait, or unseen news), as a desktop notification (OSC 9) and the terminal's bell; never for a snapshot, so reconnecting announces nothing. Control characters are taken out of the text, which can carry an issue's title.
- **Getting about:** one idea, tabs: the top bar shows the four screens as tabs (*Sessions*, *Needs you* with its count, *Tickets*, *Settings*), the one shown lit, and ⇥ and ⇧⇥ go round them from the list. ⏎ on a session gives it the keys beside the list, where ⇥ is the program's (completion, in Claude Code and shells), and Shift-Q gives them back. Ctrl-1, Ctrl-2 and Ctrl-3 go straight to a tab from anywhere, a session's terminal included, since no program there uses them; terminals tell Ctrl and a number from the number only with the kitty keyboard protocol (without it, Ctrl-3 is Esc and Ctrl-2 a NUL), so on the list the plain numbers work too. *Settings* is `4` on the list only (with Ctrl or without): without the kitty protocol Ctrl-4 and Ctrl-\ are the same byte, which a session's program may want. Esc and Backspace go back to *Sessions*, where they do nothing; in a session's terminal they reach the program.
- **Needs you:** sessions asking something first, then sessions with unseen news, oldest first. Looking at a session clears it, so the selected entry holds its place until the selection moves on.
- **Tickets:** a third view (`i`, or ⇥), each project's open tickets (`ListIssues`, GitHub issues through the person's `gh`, fetched when the view first shows a project and again on `r`) and, for the selected one, its text (`ViewIssue`, fetched once). The agents on a ticket are the sessions in the project's worktrees on branches named for it (`muster_core::tickets::issue_of_branch`: `muster/issue-<n>`, `-<title>`, `-2`…), so nothing new is stored. ⏎ opens the agent on it (the latest still running, else the latest) or starts the first (`StartFromIssue`: its worktree, made or found, and the coding agent the person chooses in a dialog, the one last chosen on a ticket offered first and never a shell, with the ticket fenced as data); `a` starts another, chosen the same way, in a worktree of its own (`another`: `…-2`, `…-3`, skipping branches the repository has); `b` opens it in the browser (http and https only). Each agent's line in its details says what it has used, after its status, and the *Agents* heading what they all have together (a cost only where every one reports its own, as a part would read as the whole); each line ends with the pull request from its worktree's branch, and the ticket's line with the one that says most of how its work stands (merged, then open, then a draft, then closed; the newest of each), compact, where its title keeps twelve characters beside it. A session opened from it leaves the person on it when they come back. `x` closes the selected ticket on GitHub (`CloseIssue`, `gh issue close` off the Supervisor's loop, refused for a plain folder), after asking, since everyone watching it is told: the one change Muster makes in a tracker, and only when the person asks. The ticket then leaves the list, and if it has worktrees the UI offers to clean up: it stops the agents still running there and removes each worktree once nothing runs in it (`RemoveWorktree`, keeping the branch; one with uncommitted changes is asked about, as for any worktree). Jira Cloud and Linear go behind the same `TicketSource` trait. Projects share their tickets (`app::sharing`) where their listings say the same `source` (`Reply::Issues`, protocol 21): a tracker that is no repository's own and the same query, `jira <site> <JQL>` (*only my tickets* in it) or `linear <team> <mine|all>`; GitHub's and GitLab's issues have none, and a daemon before 21 sends none, so nothing is shared. An agent asked for with `a` gets a worktree of its own only where the ticket already has one; elsewhere it is the ticket's first. (The autopilot's Runs view and run keys were taken out of the UI when it was set aside; they are in git history, step 10.)
- **Settings:** a fourth view, each project and under it the settings the person changes as they go: *Only my tickets* (`[tickets] mine`), *Branches with muster/* (`[branches] muster_prefix`, toggled like it; `SettingChange::MusterPrefix`, protocol 20, the row shown only by a daemon of 20 or later, and a change fetching no tickets) and *Tickets from* (`[tickets] tracker`, with `site` and `project` for Jira, `team` for Linear). ⏎ on *Tickets from* opens a dialog: ⇥ and ⇧⇥ go round the trackers, the git remote's first, ↑↓ between Jira's site and key, and a Jira site another project uses is offered. The choice is written whole (`SettingChange::TicketsFrom`, protocol 17, sent only to a daemon that agreed to 17), what the last tracker needed going with it and a query written by hand staying with Jira; `None` takes the keys out, to follow the repository's `muster.toml` and the git remote again. The settings read back say what is written and which file names the tracker, and whether nothing can tell where the tickets are (`tickets_untold`), which the row shows as *choose*. They are read (`ProjectSettings`: the value, whether it comes from the person's overrides, the repository's `muster.toml` or the default, where the tickets come from, and the person's file) each time the view is shown and on `r`, since a file may have been edited by hand. ⏎ or space turns the selected setting on or off (`ChangeSetting`); the row shows it is being changed and takes no second press until the answer, which carries the settings as they stand after. The project's tickets are then fetched again, and the Tickets view says when a project's are only the person's (`Issues { mine }`). A refused change is said, and the settings read again.
- **Adding a project:** the path field is also a folder browser: below it, the folders in the folder typed so far, narrowed by the name after its last `/` (ignoring case, matches at the start first, hidden ones once a `.` is typed), with git repositories marked; typing a name chooses its first match, and ⏎ adds the chosen folder or else the typed path. A repository is a folder with a `.git` inside, except that on macOS the home folder's Desktop, Documents and Downloads are not looked into to mark them, since that makes macOS ask whether the terminal may read them, three questions for opening the dialog at home. Names holding control characters are left out: drawn, they would reach the terminal as commands.

A worktree's line ends with its summary before its pull request; short of room the pull request's word goes first, then the summary, then the branch is cut short. Its details say it in words (`Changed +120 −30 in 5 files`). Where its work meets other work in the project, the line says `conflict` (red) or `overlap` (yellow) before the summary, which stays as the rest gives way; its details and the top of its changes pane (*Other work on these files*) give a line to each other workspace: where it would conflict, or the files both change, three named and the rest counted. The pane takes these from the state as it changes, asking the daemon nothing. Under the change are the workspace's turns (`app::timeline`), asked of a daemon of 25 or later and again whenever the workspace's newest entry changes: each with its number, what it was (`Claude Code · turn 3`, the edits between turns, or what an undo put back), how long ago it ended and what it changed; ↑↓ choose files and turns alike, and ⏎ shows a turn's diff. `z` on a turn asks the daemon what putting the files back would do (`UndoPlan`) and the person whether to (`Dialog::Undo`, with the pane behind it): what later entries go with it, that what is there now is kept, that the agent still remembers the turn, and, where the branch has moved since, whether `b` moves it too or why it stays. Only `y` or `b` sends `Undo`.

## 5b. Notch

- **What:** on a MacBook with a notch, the agents shown around it while the person looks away from every Muster window (`PRODUCT.md` §6). `muster-notch`'s `board` says what to show from the state alone: shown while no client is looked at (`Snapshot::looked_at`), Muster's own settings have it on, and a session works, asks or has news not seen; how many wait on the person and how many work; the sessions waiting (questions, then news, each oldest first) and then those working, at most eight, the rest counted. Its `geometry` finds the notch from what AppKit says of each screen (the top safe-area inset is its height; the screen's width less the menu bar's room either side, `auxiliaryTopLeftArea` and `auxiliaryTopRightArea`, its width) and places the panel. Nothing can be drawn in the notch itself, which has no pixels, so at rest the panel is the notch's own height with a slim side of 30 points either side in the menu bar's row, black like the notch, so what it says reads as part of it and the notch looks no thicker; pointed at, the list opens down from the notch at that width, two rows of text to a session. Both are pure and unit-tested on any platform.
- **Looked at:** each UI says whether the person is looking at its window (`ClientFrame::Looking`, protocol 23) as it connects and as its terminal reports focus (a terminal that never reports counts as looked at). The Supervisor keeps the clients that say so (`supervisor::looking`), each held by a guard that leaves with its connection (`ARC-14`), and publishes whether any is looked at (`Delta::LookedAt`, sent only to a client of 23 or later; every delta says the protocol it came in, `Delta::since`, and the pump sends none newer than its client's).
- **Picking a session:** a click on a listed session sends `Command::Reveal`; the daemon sends `ServerFrame::Reveal` to the client looked at last (the newest, if none has been), or refuses when none is open, which the notch says under its list. The UI opens the session beside the list with the keys, and brings the person's terminal to the front with `open -b`, by the bundle identifier macOS put in its environment (`__CFBundleIdentifier`), only an identifier.
- **On screen:** a borderless, non-activating `NSPanel` two levels above the status bar, on every Space and over full-screen apps, never in the window cycle; black, its bottom corners rounded, what waits (▲, pulsing) in the left side and what works (with the spinner) in the right; text in `NSTextField` labels changed only as what they say changes; a view class of its own takes the first click without activating anything. The program is an accessory (no Dock icon, no menu bar). AppKit runs on the main thread; the link to the daemon (`link`, a current-thread Tokio runtime on a thread of its own) hands each board over on the main dispatch queue: on a change, and every motion step (100 ms) while shown, when the spinner turns, what waits pulses, times tick and the pointer is looked at (open over the panel at rest, closed once off the open one). Hidden, nothing is drawn and nothing wakes.
- **Lifecycle:** the UI on a Mac starts `muster notch --detach` once its state says the notch is on (`MUSTER_NOTCH=off` keeps it from doing so), again after reconnecting, and again when it is turned back on; that starts the notch as a process of its own, in a session of its own (`--background`), its errors in `notch.log` in the runtime directory, written afresh each start. A lock in the runtime directory (`notch.lock`) keeps it to one; a screen without a notch ends it at once. It never starts the daemon: it ends when turned off, when the daemon speaks no notch, and when the daemon has been gone 30 seconds (a restart in place is back within one). A daemon of another version has it move onto the program installed now (`exec`, with `MUSTER_NOTCH_FOR` naming that version, so it is done once).
- **Muster's own settings:** `settings.toml` in the person's settings folder, beside the projects' overrides: `[notch] show`. The daemon reads it as it starts, keeps it in the state (`Snapshot::preferences`), and changes it on the Settings screen's row (`Command::ChangePreference`, keeping the rest of the file as written), telling every client (`Delta::Preferences`).
- **Tested:** the board, geometry and the copy of the state by unit tests; the UI's side (looking, the reveal, starting the notch, the Settings row) by the app's tests; the daemon's (lookers, the pump's filter, the setting) by the Supervisor's; the whole by end-to-end tests against the real daemon (`tests/notch.rs`). What AppKit draws is checked by hand on a MacBook, as no test can see the screen.

## 6. Protocol

Copied from Nebula where it is good, fixed where it is not.

- **Transport and framing:** Unix socket `<runtime>/daemon.sock` with mode 0700. Frames are `[u32 LE length][MessagePack]`, capped at 4 MiB and checked before allocating.
- **Handshake:** `Hello { min_version, max_version, capabilities }`, answered with the agreed version or `Incompatible`. Encoded with named fields (`rmp_serde::to_vec_named`) so the handshake can grow; Nebula's positional encoding froze it.
- **Planes,** each its own enum rather than one 45-variant request type:
  - *State:* `Subscribe` returns a snapshot, then streams `Upserted`, `Removed`, `StatusChanged` and `Transitioned`. The Supervisor takes the snapshot and opens the subscription in the same step, so no delta is missed or repeated — simpler than Nebula's subscribe-before-snapshot ordering, which a single owner makes unnecessary. A subscriber that falls behind gets a fresh snapshot instead of the lost deltas.
  - *Stream:* `Attach { session, stream, from_seq }`, `Input`, `Resize`, `Detach`. Streams are a PTY's terminal output, a headless agent's raw JSONL and parsed events, and check output.
  - *Commands:* carry a `req_id` and get `Ack`, a typed reply, or `Error { code, message }` with a machine-readable code (`ARC-07`).
- **One writer task per connection,** so replies and stream frames never interleave.
- **Clients reconnect** with backoff, re-subscribe, and re-attach from their last sequence number. Nebula's TUI does not.
- **Versioning** (`ARC-09`): every schema change bumps the version; new optional fields use `#[serde(default)]`; a new variant is sent only to peers that announced support; removals bump the minimum. Until the first release, changes bump both versions instead of gating variants, so a daemon left running by an older build refuses a newer client with a message naming `muster daemon stop`, rather than misreading it.

## 7. Harnesses

A harness is **data plus a parser**, following Nebula's descriptor idea.

- **Descriptor:** id, program, interactive arguments, headless arguments, session-id and resume templates (`--session-id <uuid>`, `--resume <uuid>` for Claude Code, so Muster chooses the id up front and never has to discover it), model and permission-mode flags, how hooks are passed at launch (or none), headless output parser id, credential kind for containers, image install recipe, and which home directories a container keeps on a volume. Users override fields in their config; contradictory entries are rejected at load.
- **Hands-on agents** (`PRD-03`, `PRD-13`): each is started in its PTY and heard the way it allows without editing the person's config, and each resumes after a daemon restart from the id its reports carried.

  | Harness | Session id | Status | Resume |

  | Claude Code (`claude`) | chosen: `--session-id` | hooks in `--settings` | `--resume <id>` |

## 8. Runs and containers (M2; the autopilot, set aside)

The autopilot was set aside on 2026-10-11, at the author's call: Muster assigns agents to tickets the person chooses rather than working tickets alone. Its daemon code and tests stay, compiled and tested (also on real Docker), as does the protocol; the command line hides `muster run` and `muster auth`, and the UI no longer shows runs. A run started anyway still works as described here. The stages by hand on a workspace (*Check*, *Draft PR*, *Agent review*) are in use.

- **Run machine:** `Queued → Provisioning → Building → Checking → OpeningPr → AgentReview → ReadyForYou → Merged`, plus `NeedsYou` and `Cancelled`. Events: `SlotGranted`, `ContainerReady`, `AgentFinished`, `ChecksFinished`, `PrOpened`, `ReviewSubmitted`, `HumanApproved`, `HumanRequestedChanges`, `Merged`, `LimitHit`, `InfraFailed`, and the user's `Cancel`, `Retry`, `TakeOver`, `HandBack`. A failed check, a reviewer's requested changes and a person's requested changes each count one attempt (`PRD-02`, `PRD-12`). Pure and exhaustively tested, including the odd orders: a review arriving after a cancel, a merge while checks re-run, a limit hit during review. Built (`muster-state::run`): every transition bumps a generation; work is asked for under it and reports back with it, so a report on overtaken work changes nothing. Time counts only in the stages where Muster works on its own; a person's retry or hand-back starts a fresh budget of attempts, time and cost; a retry resumes the stage it stopped in, or a new container if the old one was lost, and the building agent gets the person's notes or else what it was told last. Taking over is possible once there is a container; handing back stops the sessions in the container and checks the person's work. Stopping work is bounded by generation: a step that stops work and asks for more (a hand-back stops the person's agent and starts the checks) stops only what was asked for under earlier generations, so the two cannot race.
- **Runtime:** the `docker` command (`containers.rs`), not the Engine API through bollard as first planned: it finds the person's runtime through their current Docker context (Docker Desktop's socket is not `/var/run/docker.sock`; OrbStack and Colima have their own), as `gh` brings their GitHub login, adds no heavy dependency, and end-to-end tests fake it on `PATH` like `gh` and `claude`. Each call runs without a shell and with a time limit; values for a container's processes go through docker's environment (`--env NAME`), never its arguments, which any process can read. A streamed `exec` dies with the daemon whichever way Docker is reached, so agents and checks run detached in the container and write to files there, which the daemon reads from a stored offset, also after a restart (`ARC-04`). Real-Docker tests run with `MUSTER_DOCKER_TESTS=1` (and CI on Linux).
- **Image:** per project, from `project.dockerfile` in `muster.toml` (built with the repository as context), or Muster's base image, built once from a recipe in the binary: Node, git and Claude Code in the version the person runs, as an unprivileged `muster` user, since Claude Code refuses to skip its permission prompts as root. Docker's own init stands in for tini. Lamphaus adds a JDK and the Android command-line SDK. `MUSTER_RUN_IMAGE` names a ready image instead.
- **Work as jobs** (`runs/job.rs`): an agent's turn or the checks run with `docker exec --detach` in a session of their own, writing `/tmp/muster/out/<generation>-<role>.{in,base,runner,pid,out,err,exit}`; the exit code is written last. The daemon reads the state and the output from an offset in one look every half second and, after a restart, finds a job by its pid file rather than starting it twice, adding its cost to the base it started from (`.base`), so nothing is counted twice. A process id is trusted only if that process carries the job's name in its environment (`MUSTER_JOB`), since a restarted container reuses ids: a job whose runner is gone without an exit code was lost with its container (Docker or the machine restarted) and stops the run for the person rather than being followed for ever. Docker's own failures (`Error response from daemon: …`) are told from the command's: a container gone or stopped ends the work at once. Stopping work kills each unfinished job's whole process group, below a generation, after leaving a mark of it that a job starting late checks once its id is written, so work overtaken while it was being started never runs on.
- **Overtaken work:** the Supervisor tells the run's work its generation as it moves (a `watch`, one writer); work asked for under an earlier one stops without a word before starting anything more, while following a job, before pushing, opening the pull request or posting a review. A reviewer killed by a stop is not asked again.
- **Settings:** read when a run starts and again when the person sends it back to work (retry, hand-back, changes asked for), refusing while they cannot be read; a run resumed after a restart with settings that cannot be read stops for the person rather than working with none, and the checks refuse to pass with no commands (`PRD-02`).
- **Branches:** a run's branch is `muster/issue-<n>-<slug>`, made unique against other runs' and against the person's own branches, local or on their remote as last fetched, so a run never pushes onto a branch someone works on. Before more work goes on a branch others can reach (it has a pull request, or was handed over), the mirror is refreshed and the container merges in what the branch gained elsewhere (a suggestion committed on GitHub, the person's later commits); a conflict stops the run for the person. A retry of a run stopped while publishing checks again first. The checks run only with the work on the run's branch, which is what is pushed.
- **Containers left behind:** a cancel removes whatever container the run may have, ready or not; one reported after its run ended is removed then; at start the daemon removes those of ended runs it knows (and no others: another daemon's are not its business). An exit of 137 (killed, as for lack of memory) during the checks or an agent's turn stops the run with that hint rather than counting as failed work. The builder runs with `--dangerously-skip-permissions` (the container is the sandbox) and resumes its conversation while the container still has the transcript; the reviewer runs with read-only tools (`Read`, `Grep`, `Glob`, `git diff/log/show/status`) and must end with a JSON verdict, asked for once more if it gives none. The checks first commit what the agent left uncommitted, so what is checked is what is pushed, and fail a branch with no commits.
- **Credential** (`PRD-06`): a Claude Code token (`claude setup-token`) stored with `muster auth claude` in the macOS Keychain, where `security` asks for it itself so it is never in a process's arguments; failing that `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` in the daemon's environment. It goes into an agent job's environment only, through docker's own, never the container's: the checks never see it (tested with `docker inspect`).
- **Pull requests as the person:** Muster pushes and opens pull requests with the person's credentials, so they are the author, and GitHub lets no author approve, ask for changes on, or be asked to review their own pull request. The reviewer's verdict is posted as a review comment; a ready pull request is marked ready and waits in Needs you.
- **Checkout without host write access** (`PRD-04`): the daemon keeps a bare mirror of each repo under its data directory and fetches before each run. The mirror is mounted **read-only**; the container clones it into `/work` on its own filesystem.
- **Commits leave as a bundle** (`ARC-06`): the daemon runs `git bundle create - <branch>` through `exec`, fetches the bundle into the host mirror, and pushes from the host with the user's own GitHub credentials. No git-host credential ever enters a container, and the agent cannot push.
- **Processes:** the container's main process is `tini` + `sleep infinity`; agents and checks are separate `exec`s, so the container survives between stages and a person can take over at any time.
- **Limits:** the container's hard memory limit equals the project's reservation. A process killed outright (exit 137, as the kernel does when memory runs out) becomes `InfraFailed` with a hint to raise the reservation.
- **Caches:** one named volume per project for build caches (Gradle, npm), shared by that project's containers; the user can clear it from the TUI.
- **Actions by hand:** *Check* (built: `CheckWorkspace`, `muster check`, `c` in the UI) runs the project's commands in a worktree or the checkout as a session of their own (harness `checks`), on the host as the person, with the workspace's own `muster.toml` and the person's overrides, stopping at the first that fails; the person watches them, starting the session again runs them again, and a failure is news like any session's. The per-command limit needs `timeout`, which macOS has only with GNU coreutils; without it a command runs until it ends or the person stops it. A run's container is not checked by hand: handing the run back checks it. *Draft PR* (built for host workspaces: `OpenPullRequest`, `muster pr`, `o` in the UI) pushes the workspace's branch, as committed, with the person's own git (never forced, and without touching its upstream setting), and opens a draft with their `gh`, or finds the one open, off the Supervisor's loop; the base is the one the settings name, or the remote's default. *Agent review* (built: `ReviewWorkspace`, `muster review`, `v`) starts Claude Code in plan mode, which changes nothing, as a session in the workspace (harness `review`), told to read `git diff <base>...HEAD` and report problems with file and line and a verdict; it stays in plan mode when resumed. A run's container does these itself. *Hand to autopilot* (built: `StartRun { from }`) makes a run of a workspace's branch, as committed, for an issue the person names: refused while the work tree has uncommitted changes (the run would leave them out), on the base branch, or on a branch another run has. The run keeps the branch's name; at provisioning the mirror takes the branch from the person's repository fast-forward only, after its refresh (which keeps only `origin`'s branches), so commits the run pushed since are never taken back. Its first container goes to `Checking` rather than to an agent; if the checks fail, the building agent carries the work on, told the branch already has commits.

## 9. Scheduler and resources

- **Two pools on macOS.** Worktree sessions use the host's memory; containers use the container runtime's VM. They are measured separately.
- **Sampling:** every 2 s a sampler task asks the Supervisor which sessions run under which process, measures each one's whole process tree with sysinfo (an agent's tools and builds are its children; a test shows a child's 200 MB counted) and the host's memory on a blocking thread, and hands the report back. The Supervisor keeps the latest in the snapshot, sends it to clients as a `Resources` delta, and stores every fifteenth in SQLite for history. Containers will use Docker's stats stream (M2).
- **Admission (M3):** the run budget is the container runtime's total memory (from `docker info`) minus a headroom, default 2 GB. Runs start first in, first out, only when active reservations plus their own fit (`PRD-05`). The queue entry carries a reason the TUI shows as it is, for example *"Waiting for 6 GB — 10.5 of 12 GB reserved by #41 and #43."* Hands-on sessions are never queued; a hands-on container session still counts its reservation against the budget.

## 10. Sources and git host

- **Where a project's tickets and pull requests are** (`ARC-03`): its settings' `[tickets] tracker` and `[pull_requests] host` (§12), else its git remote, read in `muster_core::remote` (pure): `github.com` is GitHub, `gitlab.com` or a `gitlab.…` host GitLab, `bitbucket.org` Bitbucket Cloud. A host comes with its own tracker, but Bitbucket's, retired in 2026 (its teams' tickets are in Jira), so a Bitbucket project names its tracker. A remote whose address names no host (a local path) is told apart from none; the address is never echoed, as it can carry a password. Trackers and hosts are found per project for each command (`Trackers`, `Hosts`), off the Supervisor's loop, and share one error (`ServiceError`: not configured, not signed in, not found, refused, unavailable, unreadable), each saying what to do. A service that cannot be reached over the network (an API's request failing, or `gh` and `glab` saying so) is *unavailable* with a word about the VPN a company's network may need; the UI fetches a listing that failed again when the person comes back to the Tickets screen or to its window, and on `r`.
- **Ticket keys:** a ticket is a `TicketKey`, a number (`#42`, GitHub and GitLab) or a project's key and a number (`APP-7`, Jira and Linear); nothing else is taken, so a key is safe in a branch, a command line and a terminal. Work on one goes on `muster/issue-<key>-<title>`, or `issue-<key>-<title>` where the project's branches go without `muster/` (`[branches] muster_prefix = false`, the Settings screen's *Branches with muster/*), which also names the ticket to Jira's own branch linking. Either form names the ticket to `issue_of_branch`, so branches made before a change keep their agents. A run's branch keeps `muster/`.
- **`TicketSource` trait:** list (open, newest first, with the `source` projects sharing them have alike), view (with its text), and close (the one change Muster makes in a tracker, when the person asks). With `[tickets] mine = true`, a listing has only those assigned to the person signed in: `gh … --assignee @me`, `glab … --assignee=@me`, Jira's query and `AND assignee = currentUser()` (a JQL of the person's own keeps its `ORDER BY` last), Linear's `assignee: { isMe }` filter or its MCP tool's `assignee: "me"`.
  - *GitHub:* the GitHub CLI (`gh … --json`), as Nebula uses, so the person's own `gh` login covers authentication and GitHub Enterprise, and `gh` finds the repository from the checkout's remote.
  - *GitLab:* the GitLab CLI (`glab … --output json`), the same way: the person's `glab auth login`, gitlab.com or self-managed; it never prompts (`GLAB_NO_PROMPT`, no pager or editor).
  - *Jira:* the project or JQL in `[tickets]` (a project's default: `statusCategory != Done ORDER BY created DESC`). Through Atlassian's MCP server (Rovo MCP v2, `?tools=all`) with the person's browser sign-in, for Jira Cloud: the site's `cloudId` looked up, the tools called by every name they have had (`listJiraIssueTransitions` or `getTransitionsForJiraIssue`) and their arguments named as each tool's input schema says. Or through Jira's REST API with a token: Cloud's v3 (`/search/jql`) with the person's email and API token, a Data Center's v2 with a personal access token. Descriptions read as text, whether in Atlassian's document format (REST) or as the HTML its MCP server gives, `responseContentFormat: "markdown"` asked for or not (seen 2026-10-12): `muster_core::html` keeps paragraphs, line breaks, lists, headings, links (with their address where the text is not it, http, https and mailto only), tables and code, drops tags, comments, scripts and styles, and decodes references, before control characters are taken out. Closing takes the transition into the Done status category, whatever the workflow calls it.
  - *Linear:* the team in `[tickets]`. Through Linear's MCP server with the person's browser sign-in, or its GraphQL API with a personal API key (sent as it is). Open is not completed or canceled; closing moves an issue to its team's first completed state.
  - Calls never run on the Supervisor's loop: listing answers from a task of its own, and starting work fetches the ticket on a task, then returns to the Supervisor only to create the worktree (reused if it exists) and the session (a test proves a slow `gh` does not delay other commands). Listing, viewing and closing need no repository (a folder's tickets can be in Jira or Linear); starting work does, for its worktree. The agent gets the ticket as its first prompt, set apart between marker lines and named as a description of the work, not instructions (`PRD-07`); the marker lines carry a random tag, so a ticket cannot close them early and go on as if it were Muster. Ticket text is cleaned of control characters as it arrives, and everything the command line prints from outside (titles, labels, names, paths, git's messages) is cleaned again, so no escape sequence reaches a terminal; the UI draws through ratatui, which drops them. Automatic pickup (runs, set aside; GitHub's numbered issues only) follows `PRD-07` too: the configured label must have been applied by an allowed account, checked against the issue's event timeline, not just the label's presence (M2).
- **`GitHost` trait** (`githost/`): open a draft PR (or find the branch's open one), post a review comment, mark ready or back to draft, read PR state, and find the pull request from a branch with how it stands (`pull_request_of`, below). Pushing is always git's (from the checkout by hand; from the host mirror in a run, §8). GitHub through `gh`; GitLab merge requests through `glab` (`mr create --draft --yes`, which pushes nothing); Bitbucket through its API (Cloud 2.0; a Data Center's `/rest/api/latest`, whose changes name the pull request's version) with the person's API token as a bearer token. Pull requests by hand go to the project's host, chosen before anything is pushed; runs open theirs on GitHub.
- **MCP and OAuth** (`mcp.rs`, `oauth.rs`): a small MCP client over Streamable HTTP (JSON-RPC posted with the access token; answers as JSON or server-sent events; the server's `Mcp-Session-Id` carried on). Signing in follows the MCP authorization spec: the server's protected-resource metadata (RFC 9728) names its authorization server, whose metadata (RFC 8414, the issuer's path after `.well-known`) gives the endpoints; Muster registers itself as a public client (RFC 7591) with a loopback redirect, asks for the provider's scopes (with `offline_access`), takes the code back at `127.0.0.1` bound by a random `state`, and exchanges it with a PKCE verifier (S256) for the resource (RFC 8707). The session (client id, tokens, expiry) is kept in the Keychain; an access token within two minutes of its end is refreshed and the rotated refresh token kept. Checked against Atlassian's and Linear's published metadata; the sign-in itself is the person's.
- **Waiting on people:** PR state is polled every 60 s with ETags, which do not count against GitHub's rate limit when nothing changed. Webhooks need a public endpoint and are out of scope (`PRD-10`).
- **Each branch's pull request** (`supervisor::pulls`, shown beside each worktree, §5a): on the same 60 s timer the Supervisor gathers the branches checked out in worktrees and checkouts (not detached, not a plain folder's, not a run's container) and looks them up off its loop, project by project, through the host chosen as for pull requests by hand. The branch pull requests merge into is skipped: other people's forks may well have one from it. What is found is kept on `Workspace::pull_request` and sent as `WorkspaceUpserted`, an optional field older clients pass over (protocol 18), and never stored; a look that fails keeps the last one's, logged once per project until the failure changes; a branch checked out in its place clears it at once; and a pull request opened by hand is looked up straight after. While no client is subscribed only every tenth tick looks, so a closed UI costs the host little and an opened one starts from something at most ten minutes old. Only read: nothing is changed on the host (`PRD-01`).
  - *GitHub:* `gh pr list --head <branch> --state all --limit 1 --json number,url,state,isDraft,reviewDecision,statusCheckRollup` (newest first). Its checks are folded as GitHub's page reads them: any check run failed, timed out, cancelled, needing action or failing to start, or any commit status failed or errored, fails them all; else any not completed (or a status pending or expected) keeps them running; else they passed, skipped and neutral ones included. The review is `reviewDecision`, empty when none is asked for.
  - *GitLab:* `glab mr list --source-branch <branch> --all`; an open merge request's pipeline from `mr view` (`head_pipeline`, which lists leave out), and its review from `detailed_merge_status` (`not_approved`, `requested_changes`). Checked against GitLab's API documentation, not yet a live GitLab.
  - *Bitbucket:* the newest pull request from the branch in any state (Cloud's `q` on `source.branch.name`, a Data Center's `at` and `state=ALL`), with its draft flag and reviews (a Data Center's reviewers, Cloud's participants where the answer carries them); builds are not read, so its checks go unsaid. Checked against Bitbucket's API documentation, not yet a live Bitbucket.

## 11. Secrets

- **Storage:** the macOS Keychain, through the `security` command (`muster auth claude`); nothing secret in config files or SQLite. `MUSTER_KEYCHAIN=off` leaves the Keychain alone, which every end-to-end test sets, so tests never reach the person's credential.
- **Services' sign-ins** (`secrets.rs`): Jira's and Linear's OAuth sessions, and the tokens the person gives for Bitbucket, Jira and Linear, are Keychain items under the service `muster` (`jira:mcp`, `linear:mcp`, `jira-token:<site>`, `linear-token`, `bitbucket:<host>`), never in config, SQLite or a log. An environment variable the person sets for the daemon wins (`JIRA_API_TOKEN` with `JIRA_EMAIL`, `LINEAR_API_KEY`, `BITBUCKET_TOKEN`), and is the way off macOS. `muster auth …` reads a token without echo (or from a pipe); writing one hands it to `security -i` on its standard input, never a command line anyone can read. A token never shows in `Debug`; a service's refusal is cut, cleaned and never carries it.
- **Worktree sessions:** Muster passes no credentials; the harness uses the user's own sign-in, exactly as in a terminal (`PRD-06`).
- **Containers, first:** the agent credential goes only into the agent `exec`'s environment, never the container's, so check stages do not see it. The agent's own child processes still can — acceptable on the user's own repositories only.
- **Containers, before untrusted tickets:** a host-side proxy. The container gets a per-run token and `ANTHROPIC_BASE_URL` (or the harness's equivalent) pointing at the daemon; the daemon adds the real credential.
- **Credentials in tickets** (`muster_core::credentials`, pure): someone may paste a secret into a ticket (a `curl` command with its `Authorization` header, an API key). Every tracker Muster finds for a project is wrapped (`trackers::Hidden`), so a ticket's title and text have their credentials replaced by `[hidden by Muster]` before anything sees them: the screen, an agent's first prompt, a run. Hidden: private keys, JSON Web Tokens, what follows `Bearer` or `Basic`, well-known token forms (GitHub, GitLab, Slack, Anthropic, OpenAI, AWS, Google, Linear, Atlassian, npm, PyPI), the values of keys that name a secret (`api_key`, `x-api-key`, `token`, `password`, `client_secret`, `cookie`, …) as `key: value` or `key=value`, and a web address's password. It errs towards hiding; the ticket in its tracker is left as it is (`b` opens it), and only how many were hidden is logged. Tested end to end: a token in an issue reaches neither the reply, the agent's arguments nor the log.
- **Redaction:** every stored or forwarded stream passes through a redactor that masks known secret values. An end-to-end test asserts no secret appears in SQLite, logs or streams.

## 12. Configuration

`muster.toml` in the repo, with local overrides in `~/.config/muster/projects/<project id>.toml` (`MUSTER_CONFIG_DIR`, then `$XDG_CONFIG_HOME/muster`), merged over it key by key; `muster project config <project>` shows the result and where it came from. The UI's Settings view changes the person's overrides, never the repository's file (`ARC-05`): the daemon edits the overrides' text with `toml_edit` (`muster_core::config::edit`, pure), so the rest of the file and its comments stay as written, checks that the merged settings still read, and writes the file whole (a file beside it, moved over it); a new file starts with a line saying what it is. Changes are made on the Supervisor's loop, so two never interleave in one file; reading the settings back, which asks git for the remote, runs off it. Hands-on sessions need none of it; runs and actions do, and runs need at least one check (`PRD-02`). Read strictly (`muster_core::config`): an unknown key, a size or duration that does not parse, a path that leaves the repository, or a pickup label nobody is allowed to apply is an error naming the file, never a silent default. Muster's own settings, the person's for all of it rather than a project's (`[notch] show`), are in `settings.toml` in the same folder (`muster_core::config::preferences`, §5b), read and changed the same way. Example for Lamphaus:

```toml
[project]
base_branch = "main"
dockerfile = ".muster/Dockerfile"
memory = "6g"
cpus = 4

[checks]
commands = ["./gradlew --no-daemon testDebugUnitTest", "./gradlew --no-daemon lint"]
timeout = "30m"
```

## 13. Testing

Following Nebula's strategy, which is the best part of its codebase.

- **Unit:** both machines exhaustively; parsers against recorded fixtures; scheduler admission; redactor; config parsing; harness argument building; property tests (`proptest`) of what reads untrusted input and of the session machine: the frame decoder and the terminal scanners never panic and read the same in any pieces, and no run of signals breaks the machine.
- **Fakes:** in-process, behind the traits of `ARC-03`: `FixedClock` (and Tokio's paused clock for monotonic time), `FakeHost`/`FakeHosts` for git hosts, `trackers::Fixed` and `OneIssue` for ticket sources, `FakeCredentials`/`FixedCredentials`, `secrets::Kept` for the Keychain, and `FakeWork` or `NotYetBuilt` for runs' work. End to end, programs on `PATH`: stand-in `claude`, `gh` and `glab` scripts (`FAKE_CLAUDE`, `FAKE_GH`, `FAKE_GLAB`), a **fake agent** script for the other harnesses, `/bin/sh` for a hands-on session, and a local HTTP stand-in for the services Muster reaches by their APIs. End-to-end tests need no model and no network.
- **End to end:** the real daemon binary per test, isolated directories through environment variables, an RAII guard that stops it on drop, and a raw protocol client. Hooks are tested by typing `curl` into the fake agent's terminal; the progress signal by typing `printf` escape sequences.
- **Restart:** kill the daemon with a worktree session and a run in flight, start it again, assert both come back.
- **Real Docker:** a suite gated by `MUSTER_DOCKER_TESTS=1`, run in CI on Linux.
- **CI:** on the pinned toolchain (`ARC-18`), with warnings failing the build (`CARGO_BUILD_WARNINGS=deny`, `ARC-16`): `fmt`, `typos`, `cargo shear` for unused dependencies, `clippy`, `cargo doc`, the tests through `cargo nextest` (each in its own process, with a time limit) on Ubuntu and macOS; a build on the oldest Rust Muster declares (`rust-version`); `cargo deny` for licenses, advisories, banned crates and an allowlist of dependencies that may run build scripts; a **failing** file-size check (`ARC-08`); and a scan for anything shaped like a real credential (`ARC-20`). `muster-state`'s `no_io` test fails if anything below the pure crates does IO (`ARC-01`).

## 14. Rules

- **ARC-01** `muster-core` and `muster-state` do no IO.
- **ARC-02** The daemon's state (projects, workspaces, sessions, runs) has one owner, the Supervisor; every other task asks it. Shared mutable state elsewhere is only a leaf: a cache, a client's session or a per-key lock, held within one task's request and never across a call back into the Supervisor, its size bounded by what it is keyed on (`ARC-14`).
- **ARC-03** Every system outside the daemon has one seam where a test stands in for it. In-process, a trait with a fake: the clock (wall-clock and monotonic; clippy refuses reading it elsewhere), the git host, ticket sources, credentials, the Keychain and runs' work. Where tests run the real binary, a program found on `PATH` or named in settings: `docker`, `git`, `gh`, `glab` and the agents' own CLIs; and a real pseudo-terminal running `/bin/sh`. Harnesses are a set Muster knows, described by data, not trait objects.
- **ARC-04** Containers outlive the daemon; the daemon reconciles them on boot.
- **ARC-05** Muster never writes to the user's global agent configuration or to files in their repository to make itself work; what it needs is passed at launch, inline or as files of its own in its private runtime directory that the harness is pointed at for the session. The person's files change only when they ask (`PRD-14`), as when a workspace's files are put back from its timeline.
- **ARC-06** Git-host credentials never enter a container; commits leave through `git bundle`.
- **ARC-07** Errors across the protocol carry typed codes.
- **ARC-08** No source file over 1,000 lines; CI fails above it.
- **ARC-09** Protocol changes follow the versioning rules in §6.
- **ARC-10** A transition is stored with its reason before its effects run, and every effect is idempotent.
- **ARC-11** A session's identity comes from its own secret token, never from an id the caller supplies.
- **ARC-12** No `unsafe` code but in `muster-daemon`'s `handoff::fds`: borrowing a descriptor a library owns to duplicate it, and owning one the daemon's previous version left across `exec`; and in `muster-notch`'s `mac`, where an AppKit call or a class AppKit calls back into is unsafe to Rust; each with its reasoning beside it. The workspace denies `unsafe` everywhere else.
- **ARC-13** Every task and thread has an owner that can count it and stop it. Long-lived ones are held by what started them and end with it; short-lived work runs under the daemon's task tracker, and every wait on an external system in it has a deadline. A panic is logged, never lost. Clippy refuses a bare `tokio::spawn` or `std::thread::spawn`; where one is right, an `#[expect]` beside it names its owner.
- **ARC-14** Queues and caches are bounded. An unbounded channel is allowed only where its producer is bounded, with an `#[expect]` beside it saying why (clippy refuses one without). Every entry keyed by a session, run, connection or project leaves when that entity ends.
- **ARC-15** Logs are bounded: the daemon's log starts a new file each day or when it grows past its size limit, and keeps seven; nothing is appended forever.
- **ARC-16** Lints live in `[workspace.lints]` and `clippy.toml`, and warnings fail CI. A suppression is an `#[expect(lint, reason = "…")]` saying why, citing the rule it serves where there is one; an `#[allow]`, with its reason too, only where `#[expect]` cannot work, as in code every test crate shares. A function takes at most seven arguments unless its `#[expect]` says why.
- **ARC-17** A dependency earns its place: its reason in the commit that adds it, default features it does not need turned off, and a build script only by an entry in `deny.toml`'s allowlist. Dependabot proposes updates weekly, three days after their release; an unused dependency fails CI.
- **ARC-18** The toolchain is pinned in `rust-toolchain.toml` and moved on by a reviewed change each Rust release; `rust-version` is the oldest Rust Muster still builds on, and CI checks it does.
- **ARC-19** An error is a `thiserror` type that says what kind of failure it is, so a caller can tell failures apart, with a message for the person; Muster prints errors by their `Display` alone, so the message says everything needed, the cause's included. A `String` error stays private to the module that makes it, or at the `muster` binary's edge, where it is printed; never in a crate's public interface.
- **ARC-20** Secrets (tokens, keys, the Claude credential) live in the Keychain or in variables the person sets, never in config files, the database, a log or a test fixture. In the daemon they are `Token`s or `Secret`s, whose `Debug` shows nothing and which have no `Display`; terminal and agent output is never logged. CI fails if anything in the repository is shaped like a real credential (`scripts/check-no-secrets.sh`). Implements `PRD-06`.
- **ARC-21** Releases come only from version tags, built by the release workflow, which attests each archive. `install.sh` and `muster upgrade` check an archive's SHA-256 and, where the GitHub CLI is signed in, its attestation, and install nothing on a mismatch; a build from source builds that same tag.
- **ARC-22** The notch is a client like any other: it learns everything from the daemon's state, changes nothing but through the daemon's commands, never starts the daemon, and shows nothing while a Muster window is looked at.
