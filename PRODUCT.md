# Muster — product spec

> Drive your agents yourself, or hand them a ticket and get back a reviewed pull request.

Muster is a local daemon and terminal UI for coding agents. Used hands-on, it is a cockpit like Nebula: start Claude Code, Codex or other agents across projects and worktrees, watch their status, jump into any terminal, and pick up where you left off after closing the UI. Used hands-off, it is a pipeline: it takes a ticket from GitHub Issues (later Jira), runs an agent in its own container, checks the result, opens a pull request, has a second agent review it, and only then asks a person to look. Both run side by side, and work moves between them.

This file is the source of truth for what Muster is and is not. Rule IDs (`PRD-*`) are cited in plans, reviews and tests. When an implementation conflicts with a rule here, change the rule deliberately or change the code — never let them drift.

## 1. Problem

Developers who use Claude Code or Codex every day already run several agents in parallel. Tools like Nebula, Claude Squad and Conductor make that easier: a grid of terminals, one git worktree per agent. They are good **cockpits** for hands-on work. But they stop there. Every agent still needs a person to pick the ticket, write the prompt, watch it, run the tests, open the PR, review it, and send it back when it is wrong — even for routine tickets that do not need a person until the end.

Worktrees also isolate only files. Agents still share ports, databases, caches and processes, and nothing stops two Gradle builds from exhausting memory together.

## 2. Product

Muster is a **cockpit for agents working on your tickets**.

- **Tickets.** Muster fetches each project's tickets from ticket-source plugins, Muster's own for GitHub, GitLab, Jira and Linear, and anyone's (`PRD-15`), and shows them with the agents working on each. The person assigns agents to tickets: each agent is a session of the coding agent they choose (Claude Code, Codex, …) in a worktree of its own, started with the ticket as its first prompt. Muster reads tickets, and makes one change in a tracker: it closes a ticket when the person asks it to (after asking them to confirm, since everyone watching the ticket is told), and then offers to close the ticket's agents and remove its worktrees, keeping the branches. Any other change (comments, labels, reopening) is the person's, or their agents' through the tools those already have (such as a tracker's MCP server).
- **Cockpit (hands-on).** Every agent is a *session* you can watch and type into. Sessions live in a *workspace*: a git worktree on your machine, the project's own checkout, or a container. A project is usually a git repository, but can be any folder: a plain folder has sessions and checks in the folder itself, and none of what needs git (worktrees, tickets, reviews, pull requests) until it becomes a repository. Muster shows which sessions are running, finished, or waiting for you, and keeps them alive when the UI closes, or the terminal app it ran in quits.
- **Autopilot (set aside 2026-10-11).** A *run* took a ticket through fixed stages on its own, in a container, and asked a person only once the work had passed checks and a review. It was built and tested (M2) and then set aside at the author's call: hidden from the UI and the command line's help, its code kept. The rules and stages below that concern runs describe that code.

```
Ticket → Build → Check → Draft PR → Agent review → Ready for you → Merged
           ▲       │                      │              │
           └───────┴──── failure + reason ┴──────────────┘
```

- **The stages are also tools.** On any hands-on session you can run the project's checks, open a draft PR, or ask for an agent review by hand — or hand the session to the autopilot to finish from *Check* onward. And any run's agent can be taken over by hand and given back.

## 3. Users

- **Primary:** a developer or small-team lead who already uses coding agents daily. Some days they want to steer every agent; other days they have a backlog of well-scoped tickets in a repo with tests.
- **User #1:** the author, on Lamphaus (Android, Kotlin, Gradle) and on Muster itself. Lamphaus is a deliberately heavy test: large builds, strict project rules in `RULES.md`, real release discipline.
- **Not for v1:** large teams, non-developers. Without a test suite the autopilot has little to check; the cockpit still works.

## 4. Principles

- **PRD-01 — The person assigns the work.** Muster is a terminal UI for sessions the user drives, on the tickets they choose. Nothing starts on its own: an agent works on a ticket because the person assigned it. The one question Muster puts to an agent unasked is a chat's name (§6), which the person can turn off.
- **PRD-02 — Nothing unverified reaches a person.** A run reaches *Ready for you* only after the project's checks pass and the reviewer agent approves. Failures go back to the building agent with the evidence, up to a per-project attempt limit; after that the run goes to *Needs you* with the full history.
- **PRD-03 — Bring your own agents.** Muster wraps existing harnesses (Claude Code, Codex, OpenCode, …) through one interface. It ships no model and no agent of its own, and uses the user's own subscriptions or keys. What Muster needs of an agent is data wherever it can be: how it starts, takes a first prompt, carries on after a restart, answers one question, and lists its models; so a new agent is added in the person's own settings, without a release, and code is written only for what an agent says in a way of its own (its hooks, its plugin, its records).
- **PRD-04 — The right isolation for the job.** Hands-on sessions default to a git worktree on the host: instant, with the user's own tools and sign-ins. In a project that is a plain folder, not a git repository, there is nothing to isolate with, so they run in the folder itself. Any session can run in a container instead. Runs always use containers, and a container can never write to the host filesystem.
- **PRD-05 — Resources decide, not just display.** Muster shows memory and CPU for every session and container. Runs carry a memory reservation and start only when it fits the budget; the UI always says why a run is waiting. Hands-on sessions never wait — the user asked for them.
- **PRD-06 — Secrets never leak.** Credentials Muster handles are injected at run time with the narrowest scope available, and never enter the repository, an image layer, a log, a PR, or the database. A credential someone pasted into a ticket is hidden before Muster shows the ticket or hands it to an agent; Muster is never what passes it on. A worktree session runs as the user with the user's own sign-ins, exactly as if started in a terminal; Muster adds none.
- **PRD-07 — Tickets are untrusted input.** Anyone can file a GitHub issue. Agents work only on tickets the user assigns them (and runs, set aside, picked up only tickets the user selected). Ticket text reaches agents as data, set apart and named as a description of the work, never as configuration or instructions, and never reaches a terminal with its control characters.
- **PRD-08 — Move freely between hands-on and hands-off.** Any run's agent can be taken over interactively and handed back. Any hands-on session can be handed to the autopilot from *Check* onward.
- **PRD-09 — Survives restarts.** Closing the UI never stops a session or a run, and neither does upgrading Muster: the daemon moves onto a new version in place, every session running on. Container sessions and runs also survive a daemon restart; worktree sessions come back through the harness's own resume.
- **PRD-10 — Local first.** No Muster server, no account, no telemetry. Muster talks only to the user's ticket sources, git host, container runtime and agent providers, and, when the person installs or updates a plugin, the repository they name.
- **PRD-11 — Measured claims.** Every claim about quality, speed or cost in the README is backed by a reproducible benchmark run committed to the repo.
- **PRD-12 — Bounded cost.** Every run has a time limit and an attempt limit, and a cost limit where the harness reports cost. Hitting a limit stops the run and moves it to *Needs you*; it never silently keeps spending. Hands-on sessions show what their agent has used, read from the agent's own records (every token, cached ones included, and the cost where the agent reports one), but are never stopped by Muster.
- **PRD-13 — Leave the user's setup alone.** Muster never edits the user's global agent configuration or adds files to their repository to make itself work. It passes what it needs at launch: on the command line or in the environment (for example Claude Code's `--settings`), or as a file of Muster's own, in its private runtime directory, that the harness is pointed at for that session only (for example an OpenCode plugin). Where a harness offers no such way, Muster runs it with less status detail rather than editing its config. Plugins (`PRD-15`) live in Muster's own data folder, never in the repository or an agent's config.
- **PRD-14 — Muster changes the person's code only when asked.** Muster reads what agents change; it changes the person's files, branches or commits only at their request, never while an agent works in that workspace, and only after keeping what is there in a snapshot it can be undone from. Putting a workspace's files back as they were before a turn, moving a stacked branch or tidying commits are such requests.
- **PRD-15 — A lean core; the rest are plugins.** Muster's core is the daemon, projects and worktrees, sessions (agents' chats and shells) with their status and *Needs you*, the layout, keys and Settings, and the plugin system. Everything else is a plugin: ticket sources, panels and hooks first. New features are written as plugins, and existing ones move out one at a time as the plugin interface grows. Muster's own plugins use the same interface as anyone's, and the community's are as welcome. The person installs, turns on and approves every plugin (`PRD-01`), after being shown everything it will run; one whose manifest changes is turned off until they approve it again. A plugin never starts, prompts or types into an agent, gets no credential it did not name (`PRD-06`), and its tickets pass through the same guards as Muster's own (`PRD-07`). A plugin's hooks hear what happens (an agent needs the person, finishes or ends, a worktree, a pull request, a clash, a ticket assigned) and are told names and ids only, never a ticket's text, a prompt, an agent's output or code; there is no way back from a hook into Muster, so it only hears, each run with a deadline. Muster runs no installer of a plugin's.

## 5. Run stages (autopilot, set aside)

| Stage | Enters when | Does | Leaves to |
|---|---|---|---|
| **Queued** | A ticket is picked up | Snapshots title, body, comments and labels; waits for a memory slot (`PRD-05`) | Build |
| **Build** | A slot is free | Starts the container, checks out a fresh branch `muster/<ticket>-<slug>`, runs the building agent headless with the ticket and project instructions | Check, or Needs you on a limit |
| **Check** | The agent says it is done | Runs the project's configured commands (format, lint, test) inside the container | Draft PR on success; Build with the failing output otherwise |
| **Draft PR** | Checks pass | Pushes the branch and opens a **draft** PR: summary, ticket link, check results | Agent review |
| **Agent review** | Draft PR exists | A reviewer agent (ideally a different harness, `PRD-03`) reads the ticket and diff and posts a PR review: approve, or request changes with line comments | Ready for you on approve; Build with the comments otherwise |
| **Ready for you** | Reviewer approves | Marks the PR ready and requests the user's review | Merged; or Build when the person requests changes |
| **Needs you** | Any limit is hit, or something needs a decision | Waits with the evidence: history, logs, diff, why it stopped | Build (retry with notes), Take over, or Cancelled |
| **Merged / Cancelled** | — | Stops and removes the container; keeps the record | — |

Every transition is recorded with its reason, so the timeline of a run is always explainable.

**By hand.** *Check*, *Draft PR* and *Agent review* are also actions on any hands-on session. They run where the session lives — in its worktree or its container — and report back to the session instead of moving it along. *Hand to autopilot* starts a run at *Check* with that session's work.

## 6. Interface

Terminal UI first (ratatui). The daemon exposes the same API to any client, so a web UI can be added later without changing the daemon.

- **Sessions** (home) — projects, then their worktrees, then session cards with live status: running, finished, waiting for you, what each agent is doing as its hooks tell (`editing view.rs`, `wants to run npm`), and for how long. Each card is a chat: its agent's logo (a picture where the terminal draws them, its mark in the agent's colour where it does not) and its name: at once the first line of the first prompt it was given (in the dialog that started it, or typed in its terminal where the agent reports that), credentials hidden, and a few seconds later two to four words an agent wrote for it from that prompt; where the prompt is only a few words and its agent reports its answer, it is named once more as its first turn ends, from the prompt and the start of the answer. A name the person gave it, on one key, is never replaced. The name is asked of the session's own agent, or of the agent and model the person picks on the Settings screen, as one question with no tools, none of the project's files or instructions, and nothing kept in that agent's history, with the person's own sign-in (`PRD-03`, `PRD-13`); only the prompt (and the start of the answer) goes, credentials hidden (`PRD-06`), and an agent that cannot answer one question leaves the first line as the name. A ticket's agent is named for its ticket, and a shell for the program in front in it (`zsh`, `bun`, `cargo`), as it changes. A card takes two lines, its name whole on the first and what it is doing and for how long under it, or one where the person says, so twice as many fit. Muster draws in its own soft colours, one accent lighting what has the person's keys, the same in any terminal, or in the terminal's own where the person says; the list and the session beside it are each framed, and only the frame of the one with the keys is lit, with the list's selected line lit too while the list has them. Each project's and worktree's line folds away what is under it on one key or a click, and folded says how many sessions it hides and how the most urgent of them stands, in the same marks (waiting on the person first, then news not seen, then working); unfolded, each session's mark is on its own line only. The keys need not be learnt first: a right-click on a line offers what can be done there, each with its key, and one key shows every key of the screen shown, narrowed as the person types; every key can be set otherwise on the Settings screen, and the hints, the help and the menus show the keys as set. A count of agents working, waiting and done stays in view on every screen, and each project keeps a colour of its own. The selected session's live terminal is beside the list where it fits, one key (or a click) from typing in it, and one from full screen. The list is at first only as wide as its lines need, about 26 to 36 columns, and one key, which works while typing in the session too, folds it away so the session takes the window's width, and brings it back. The panels (the list, the session's agent, its shell, a workspace's changes, and a plugin's panel while one is open there) are laid out as the person likes: a panel dragged by its title goes to the left, the right or the bottom of the window, or beside or under another, the place lighting up as the panel would land there; the line between two panels is dragged to make one wider; the title or line under the pointer lights up, and the pointer becomes arrows over a line and a hand over a title (in terminals that let a program set it: iTerm2 3.7 or later, kitty, Ghostty), so what can be dragged shows before it is pressed; and each move has a key too. The layout is kept in the person's own settings, and put back as it first was on the Settings screen. In a window too narrow for the layout, the list folds away first and then the other panels open over one another; under a hundred columns (unless the person sets another width) the list takes the window, and the key that would type beside it opens the session over it instead. The layout comes back as the window widens. One key opens a shell in the selected session's workspace, where the person last put it (at first beside its agent), both live, or goes to the shell already there (a workspace has one): run the app, the tests or git there while the agent works. Where the window is too narrow for them all, the list folds away; where it is too narrow for two, the shell opens over the agent. A click, or one key, moves the keys between them. A shell keeps running when the UI closes, like any session, ends with its workspace, and is not counted among the agents. In the list it stands by the chats rather than among them, on one line, its prompt mark and what runs in it: under its worktree's chat where the worktree has one, as one with an agent at work in it does, set in like a part of it; after the chats where several share the workspace, as its shell serves them all. With one session open in two Muster windows of different sizes, its program takes the size of the window the person used last, so the two never resize it back and forth. A window that cannot keep up with a session's output, over a slow link say, is brought to where the session is now rather than played back everything it missed. Dragging over a session's text copies it, and only it, not the list beside it. A program there finds a terminal like the person's own: asked its colours, it says the person's terminal's, so an agent chooses a light or a dark theme to match; what an agent copies reaches the person's clipboard while they look at it, as text, but nothing there can read their clipboard; and a program that follows its terminal's focus is in focus while its session is on screen, beside the list or filling the window, and told as the person shows another or looks away from the window, so an agent that suggests the person's next prompt as a turn ends suggests it while they watch; and the terminal's size is known in pixels too, where the person's terminal says its own, for programs that size pictures by it. Each worktree shows the pull request from its branch as its git host last said, looked at about every minute: its number, whether it is a draft, open, merged or closed, and while it is open how its checks and its review stand; one key opens it in the browser. Muster only reads it there. Each worktree's line also says what its work comes to (`+120 −30`), looked at again as an agent's turn there ends, and one key shows it in a panel of its own, beside the session (in a window too narrow for both, over it): what is not committed yet, the branch's commits since it left the branch it merges into, and the files they changed, each with its lines, and any file's diff. Muster only asks git: nothing in the worktree changes, and none of the code is stored or logged (`PRD-06`). Beside them is the worktree's timeline: each agent's turn there, from the moment it began to work to the moment it stopped, whatever the agent, with what it changed, and what changed between turns (the person's own edits, or another program's); any one's diff is a key away. Muster keeps these snapshots in a store of its own, never in the repository, the last hundred of each worktree, and lets them go with it. On one key, after the person says yes, the files go back as they were before a turn, and the branch too where it has moved since and its commits are not pushed; never while an agent works there, and what was there is kept first, so this can be undone as well (`PRD-14`). The agent still remembers the turn, and Muster says so. Where the work in two of a project's workspaces changes the same files (two agents' worktrees, or an agent's and the person's checkout), both lines say so, and say more where git's own merge says merging both would conflict there; the details and the changes beside the list name the other workspace and the files. It is looked at again as each turn ends, and asks git in Muster's own store, so nothing in either workspace changes (`PRD-14`); a branch whose pull request has merged is no longer compared. On one key the person has the agent they pick tidy a branch's commits not pushed yet into clear ones (never while an agent works there, nor over changes not committed); its turn is in the timeline like any other, so it can be put back, and once it stops Muster checks that the files are as they began and says so on its session (`PRD-14`). Each session's pane says what its agent has used so far, its tokens and, where the agent reports it, its cost (`PRD-12`). A plugin's panel (`PRD-15`) opens beside the session selected on its key, the one its plugin suggests unless the person sets another, and the same key puts it away again; a panel of the workspace's opens on the worktree or checkout selected. It is a program of the plugin's, run in the session's workspace and told what Muster knows of the session (its project, branch, conversation and transcript), with none of the person's variables but those its plugin names; a chat shows only the panels opened beside it, or on its workspace. Where it cannot open, Muster says why: the plugin is off or changed since it was approved, a program it needs is not installed (and how the plugin says to get it), or what it needs is not there yet ("this session has no transcript yet"). It takes the keys on a click, as the shell does, and ends with its workspace as a shell does. A line's right-click menu lists its panels with their keys, the help lists them, and Settings › Keys sets them under their plugin's name. Start a session from a prompt, in a new worktree or the project's checkout (in a plain folder, the folder).
- **Tickets** — each project's open tickets, with the agents on each, how they are doing, what they have used, and the pull requests they opened. The selected ticket shows its text and its agents. Assign an agent to a ticket (a worktree for it and the coding agent the person chooses, the last one chosen offered first, with the ticket as its first prompt), open the agent on it, or add another in a worktree of its own. A new worktree can be made on top of another worktree's branch rather than the base, so an agent builds on work not merged yet: its work is measured, reviewed, tidied and opened as a pull request against that branch, and on one key, after the person says yes, it moves onto that branch's newest commit, or onto the base once that branch has merged, its own commits replayed there; never while an agent works there, nothing changed where one would conflict, and what was there kept first, so the move can be undone (`PRD-14`). The same key moves a branch that is not stacked onto the newest of its base. Projects whose tickets are in the same place, a tracker that is no repository's own (one Jira project's, one Linear team's, listed alike, *only my tickets* too), share them: a company's repositories often take their tickets from one Jira project with nothing in a ticket to say which repository it is for. They are listed once, under one heading naming them all; a ticket's agents are those in any of them; and assigning an agent asks which project it is for, the one last chosen for tickets from there offered first.
- **Needs you** — one queue for everything waiting on a person, oldest first: sessions asking a question, or finished and not yet seen. This is where the user starts their day. A permission the person declines, or a turn they stop, leaves it within seconds, though Claude Code says so only in its own record of the conversation, which Muster only reads (`PRD-13`). A turn that finishes is told only once it has stayed finished a moment, so an agent that goes straight back to work raises no alarm, and one key goes to the session that needed the person last. The person is told when a session newly needs them while they look away from every Muster window, once for each wait: on a Mac by a notification of the Mac's own, sent by Muster's helper (a small app of Muster's own, which a Muster window starts and which runs on while the daemon does), so it comes in any terminal and with every window closed, once the person has allowed Muster's notifications when macOS asks, and a click on it opens that session in the Muster window looked at last; elsewhere by the terminal of a window that is open, as a desktop notification and its bell. The person chooses what they are told of: questions (a question, a permission, a form), finishes and errors, each on or off, and on a Mac each with a sound of its own (the Mac's, none, or one of the Mac's sounds, heard as they choose it, or one of theirs). A notification of the Mac's own says where as its title (the project and the branch), the chat under it, then what happened, kept with the others of its project. Notifications are turned off on the Settings screen.
- **Notch** — on a MacBook with a notch, the agents shown at it while the person looks away from every Muster window and an agent works or waits on them, level with it in a slim side either side, black like it, its top corners curving into the screen's edge as the notch's do, so it reads as part of the notch, which itself can show nothing (it has no pixels): on the left how many ask the person something (or, with none asking, how many troubles there are in the work), drawing the eye for a few seconds when something new comes and then still; on the right how many work, beside a gently breathing mark, or once none works, how many finished unseen. It is in Muster's own soft colours, and with the person's Reduce Motion setting nothing in it moves but a fade. Pointed at a moment (not as the pointer passes on its way to the menu bar), or clicked, it eases open downwards into the list of them, its lines coming in one after another, wider than the notch only below the menu bar's row: those asking the person first, then the trouble in the work (two workspaces whose work would conflict were both merged, named with the file; an open pull request whose checks failed), then those with news, a rule, and those working, each with its agent's logo and its name as in the UI, its project, what it is doing (a long path cut in the middle, so its file shows), what its work comes to (`+120 −30  #88 ✗`) and for how long; the line pointed at is lit, and a click on one brings the Muster window looked at last to the front with that session open and closes the list. When something newly needs the person while they look away (a question, a conflict, failed checks), the notch opens on its own for three seconds to show just that, then closes, unless they point at it; what was there when they looked away does not. A screen reader reads each count and line in words. It goes when the person looks back at Muster or nothing works or waits, stays after the UI closes while the daemon runs, and is turned off on the Settings screen. It shows only what the UI shows and changes nothing (`PRD-01`).
- **Settings** — each project's settings that the person changes as they go: *only my tickets*, whether the Tickets screen lists only the tickets assigned to the person, in whichever tracker the project's tickets are; and *tickets from*, the tracker its git remote says or a ticket plugin the person names, Muster's own or one they installed, with what it asks for (Jira its site and a project's key, Linear a team's key), which is how a project whose remote is on a company's own server, by an address that names no tracker, gets its tickets; and *branches with muster/*, whether the branches Muster makes start with `muster/` (`muster/issue-42-fix-the-login`) or go without it (`issue-42-fix-the-login`), for a team whose branches follow names of their own. A change goes into the person's own settings for the project, never into its repository (`PRD-13`). Then Muster's own, the person's for all of it: on a Mac, *agents in the notch*; *session beside the list from*, the fewest columns a window has for a session to sit beside the list (or at any width); *colours*, Muster's own, soft and the same in any terminal, or the terminal's own, to follow its theme; *lines for each session*, two, so a session's name fits with what it is doing under it, or one, so twice as many fit; *your agents*, the coding agents the person added in Muster's own settings file, with what in it does not read named, and read again on the person's word after an edit by hand; *chats named by an agent*, on until the person turns it off, with what it costs said beside it: it asks the agent they pick, with their own sign-in and a little of their plan, and sends only a chat's first prompt (where that is only a few words, the start of its first answer too), credentials hidden; *named by*, each session's own agent or one they pick among those that answer one question, and *its model*, one of those the agent lists or one they type; *notifications*, on or off, and under it *questions*, *finishes* and *errors*, each on or off with its sound; *plugins*, under Muster's own, Muster's own plugins and those the person added, each on a line with its version, where it is from (built in, git or a folder), whether it is on, and why one is off or else what it brings (its panels with their keys, a ticket source, its hooks), and beside it everything it runs (each hook with the events it hears, its filters and its deadline), the programs it needs and whether they are found, the variables and secrets it is given and its manifest's hash: one key turns one on or off, refused with why where it cannot run (its manifest changed since it was approved, so the person updates it or links it again); one adds one from a git repository's address or a folder of the person's, and one updates one, each after fetching it, which the person can give up waiting for, and showing everything it would run and asking (`PRD-15`); and one removes one after asking, Muster's own only turned off; a change made on the command line is marked there, with when; *layout*, to put the panels back as they first were; and *keys*, every key of every screen by what it does, grouped by screen: the person presses another key for any, which is refused where that screen already uses it for something else, and puts any back as it was; a key set for something Muster no longer has, as a removed plugin's, does nothing and is said to, and the rest of the settings read as written. In a session every key goes to its program but the few that leave it, change tab or fold the list, which are set here too.
- **Resources** — host memory and CPU, and each session's usage.

## 7. Integrations

| Kind | v1 | Later |
|---|---|---|
| Ticket sources | Plugins (`PRD-15`), Muster's own for: GitHub and GitLab issues (the person's `gh`, `glab`); Jira (Cloud through Atlassian's MCP server with the person's browser sign-in, or Cloud and Data Center with a token); Linear (its MCP server, or an API key) | Any other as a plugin |
| Git host | GitHub, GitLab, Bitbucket (Cloud and Data Center, with a token) | Others behind the same interface |
| Harnesses | Claude Code, Codex, Gemini CLI, OpenCode, Copilot CLI (hands-on); any other through the person's own settings (hands-on, with less status detail, `PRD-13`; with how it answers one question and lists its models, it can name chats) | Headless runs beyond Claude Code |
| Container runtime | Docker API (Docker Desktop, OrbStack, Colima on macOS; Docker Engine on Linux) | Podman |

Each kind sits behind one interface from day one, so adding Jira or Codex never touches sessions or tickets.

## 8. Milestones

Each milestone ends with a demo that works on a real repository, and with tests that prove it.

1. **M1 — Cockpit.** The daemon owns hands-on Claude Code sessions in git worktrees. The TUI shows projects, worktrees and session cards with live status, the live terminal, and *Needs you*. Sessions start from a prompt or a GitHub issue. Closing the TUI stops nothing; restarting the daemon brings sessions back through Claude Code's resume.

## 9. Not in v1

- An agent or model of Muster's own (`PRD-03`).
- A web UI (the API keeps it possible).
- Windows.
- Teams, accounts, or any hosted service (`PRD-10`).
- Merging to the default branch without a person's approval.
- Cloud or Kubernetes sandboxes.

## 10. Success measures

- **Cockpit:** the author's daily driver; time from "needs you" to the user seeing it; no session lost to a closed UI or a daemon restart.
- **Autopilot:** share of runs that reach *Ready for you* without a person; share of ready PRs merged without further changes; median time from pickup to ready; cost per merged PR.
- **Engineering:** end-to-end tests that drive a real daemon, real PTYs, real containers and a fake harness; restart survival tested; no secret ever found in logs, images or the database (tested).

## 11. Open questions

- **Agent sign-in inside containers.** Checked 2026-10-11:
  - *Claude Code* documents `claude setup-token`, which prints a one-year OAuth token for CI and scripts, passed as `CLAUDE_CODE_OAUTH_TOKEN`. It needs a Pro, Max, Team or Enterprise plan. `ANTHROPIC_API_KEY` and `apiKeyHelper` (for rotated or vault-fetched keys) also work. `--bare` mode ignores the OAuth token.
  - *Codex* documents `CODEX_API_KEY` for `codex exec`, with `--json` for JSONL events. Saved ChatGPT sign-in is described as an advanced option for trusted runners.
  - *Risk:* anything the agent runs — including the project's own tests — can read a credential held in the container's environment. OpenAI's own guidance warns against exposing the key to repository-controlled code. For `PRD-06`, the likely answer is a host-side credential proxy: the container gets only a per-run token for a local proxy (`ANTHROPIC_BASE_URL` / equivalent), and the proxy adds the real credential. M2 may start with per-exec environment variables on the user's own repositories, with the proxy required before running tickets from anyone else.
- **Headless runs.** The architecture assumes run agents are headless with structured output, and interactive only on take-over (`ARCHITECTURE.md` §7). The container spike during M1 confirms it.
- **Status for hands-on sessions without editing config.** Claude Code accepts hooks through `--settings` at launch (`PRD-13`). Checked one by one on 2026-10-12: Gemini CLI reads hooks from a defaults file named in its environment, OpenCode loads a plugin named in its environment, Copilot CLI loads a plugin folder named on its command line; Codex runs hooks passed at launch only once the person has trusted them, so Muster hears it through its turn notice and its window title instead. Where none of this works, status falls back to the terminal's progress signal and process state.
- **Claude's trust prompt in every worktree.** Checked 2026-10-11 with Claude Code 2.1.296: accepting the prompt in a worktree records the trust against the repository's main checkout, so a repository's other worktrees, and later ones, are not asked again. The prompt therefore appears once per repository not yet trusted. Muster must not answer it or edit Claude's own files to avoid it (`PRD-13`). Claude Code runs no hook while it shows, so a session that has not announced its start within 10 s (it does in under a second) reads as *needs you: asking before it starts*, which also covers a sign-in or first-run setup.
- **Background work at a turn's end.** Claude Code 2.1.291's `Stop` payload carries `background_tasks` (empty in the one capture so far). If it lists background shells and subagents still working, it could replace part of the subagent-drain timing in the status machine. Needs a capture with background work running.
- **Notifications of the Mac's own** (checked 2026-10-20, macOS 26.5). macOS shows notifications only for an app, and asks the person only for one opened through its launcher (`open`) from where apps live: run directly, or from a temporary folder, the same app was refused without a word. So Muster's helper runs as `Muster.app` in Muster's data folder, signed for the person's machine alone, and asked. A refusal macOS has recorded for Muster is changed only by the person, in System Settings, Notifications, Muster. A click reaching Muster is still to be seen on a machine where Muster is allowed.
- **Naming without the person's hooks** (checked 2026-10-20). Claude Code's `--bare` would skip the person's hooks and plugins but does not take a subscription's sign-in; `--safe-mode` does both: with `-p`, no tools, `--strict-mcp-config` and `--no-session-persistence`, run from a folder of Muster's own, a hook passed in its settings did not fire and nothing was left in its history (Claude Code 2.1.303). Codex's `exec --ephemeral` without the person's config or rules kept nothing either (0.162.1). Gemini CLI, OpenCode (whose `run` keeps the question in its history), Copilot CLI and others are asked once each is checked the same way.
- **Heavy builds.** Android/Gradle in Linux containers needs a large image and several GB per build. Shared dependency caches between containers may be required for Lamphaus to be practical.
